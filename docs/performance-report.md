# Performance Report — Task 017

Measured, not estimated. Every number below was produced on the machine
described below by running the shipped binaries or the shipped test harness;
nothing is extrapolated.

## Environment

| Item | Value |
| --- | --- |
| Machine | MacBook Pro, Apple M2 Pro, 32 GiB RAM |
| OS | macOS 15.x (Darwin 25.x), Apple Silicon |
| Toolchain | rustc 1.98.1, cargo stable |
| Profile | `--release` unless explicitly marked *debug* |
| Workspace | fixture scale configurations generated by the `#[ignore]`d tests in `crates/application/tests/workspace_validation.rs` |

## Methodology

- **In-process use-case latency** is measured with the shipped
  `#[ignore]`d measurement tests, which build a `Config` at the target scale
  and call the use case in a loop with `std::time::Instant`, reporting the
  elapsed time. Run them with:

  ```bash
  cargo test --release -p service-orchestrator-application \
    --test workspace_validation -- --ignored --nocapture --test-threads=1
  ```

- **Idle memory** is the resident set size (RSS) sampled once per second from
  `ps` while the release binary sits idle: `service-orchestrator daemon`
  against a fixture configuration with a connected client, and
  `service-orchestrator tui` on an empty terminal.
- **End-to-end IPC latency** is measured by a Unix-socket client speaking the
  daemon's length-prefixed protocol against a real
  `target/release/service-orchestrator daemon` process, calling
  `validate_workspace` five times over one persistent connection.
- Figures are single-run observations unless a range is given; the workloads
  are CPU-bound and microsecond-scale, so run-to-run variance was under 5 %
  except where noted.

## Workloads and results

### Idle memory (release)

| Process | RSS (min–max over 10 samples) | Notes |
| --- | --- | --- |
| `daemon` (fixture config, one connected client) | **5 536 KiB ≈ 5.4 MiB** (constant) | No drift over the sampling window |
| `tui` (empty terminal, no workspace root) | **4 880–4 928 KiB ≈ 4.8 MiB** | Exits cleanly (code 0) on `q` |

Both are far below any resource concern for a local developer tool; the
daemon holds a fixed baseline because it keeps task and log state in bounded,
pre-allocated structures.

### Read-path use-case latency at documented scales (release, in-process)

`ScriptedProbe` answers all environment probes from memory, so these figures
isolate the application core's own cost — no filesystem, `PATH`, or socket
time is included. Real-probe cost is measured separately below.

| Scale | `list_services` | `get_workspace_status` | `validate_workspace` |
| --- | --- | --- | --- |
| 10 services + 2 libraries | 5.6 µs | 1.7 µs | 16.5 µs |
| 40 services + 10 libraries | 20.4 µs | 5.9 µs | 62.9 µs |
| 100 services + 25 libraries | 49.8 µs | 12.1 µs | 176.5 µs |
| 200 services + 50 libraries | 96.0 µs | 22.0 µs | 360.2 µs |

All three scale roughly linearly with entity count. `validate_workspace` is
the most expensive because it touches every service and library (path, Git
metadata, runtime, dependency, and port checks), but even at 200 services it
completes in ~0.36 ms — imperceptible over an IPC round trip.

**Repeated-call stability.** Ten consecutive `validate_workspace` calls over
100 services + 25 libraries took **1.795 ms total (179.5 µs per call)** —
identical to the single-call figure, i.e. no per-call growth, no accumulating
state.

### Configuration loading (release, real TOML files)

Fixture documents written to disk and parsed by the real loader:

| Scale | Document size | Load time |
| --- | --- | --- |
| 10 services | 5 019 B | ~199 µs |
| 40 services | 20 579 B | ~0.71 ms |
| 100 services | 51 464 B | ~1.73 ms |
| 200 services | 103 389 B | ~3.58 ms |

Loading is the single most expensive per-operation cost in the system and
grows slightly faster than linearly (validation passes over the parsed
document dominate). It happens once per daemon start, so ~3.6 ms at 200
services is acceptable; it would matter if it were ever moved onto a hot path
— it must not be.

### End-to-end IPC validation (release, real daemon, real probes)

`validate_workspace` against the developer's live configuration (7 services,
3 repositories genuinely missing, real `SystemWorkspaceProbe` filesystem
checks) over one persistent Unix-socket connection:

| Call | Latency |
| --- | --- |
| 1st (cold) | 2.48 ms |
| 2nd–5th (steady state) | 0.21–0.24 ms |

The cold call includes one-time initialization; steady state is dominated by
the loopback socket round trip and the real filesystem probes. The report
itself is correct and read-only (see `docs/workspace-validation.md`).

### Debug-profile reference

For developers running `cargo run` without `--release`, the same
`validate_workspace` scale test measured **~1.35 ms at 100 services** and
**~5.37 ms at 200 services** — roughly 7–15× the release figures. Debug builds
remain perfectly usable; they are simply not the numbers to quote.

## Bottlenecks and observations

1. **Configuration loading dominates start-up.** At 200 services a full load
   takes ~3.6 ms of pure parsing/validation. This is a start-up-only cost and
   is currently the largest single latency in the product. If configuration
   hot-reloading is ever introduced, the loader should be profiled first and
   caching considered.
2. **`validate_workspace` grows linearly** (~1.8 µs per service+library pair
   at scale) and additionally probes the real environment per repository in
   production. At the documented 100–200 service scales this stays well under
   a millisecond in-process; a future workspace with thousands of entities
   would be the first point worth revisiting (e.g. parallelizing probes).
3. **Port probing is the only I/O with a timeout.** Each occupied-port check
   is a loopback TCP connect capped at 150 ms, and checks run per declared
   port. A configuration declaring many ports on a machine that *drops*
   rather than rejects loopback connections could accumulate up to 150 ms per
   port; on macOS loopback rejects immediately, so this was not observed.
   Documented as a known worst case, not a measured problem.
4. **Memory is flat and small.** Both long-running processes sit at ~5 MiB
   with no growth during the sampling window; bounded log and task stores
   prevent accumulation (`docs/observability.md` retention limits).

## How to reproduce

```bash
# Use-case latency + config-load scale measurements (release):
cargo test --release -p service-orchestrator-application \
  --test workspace_validation -- --ignored --nocapture --test-threads=1

# Idle daemon/TUI memory: sample RSS while the release binary is idle.
cargo build --release
target/release/service-orchestrator daemon --config <fixture-config> &
ps -o rss= -p <daemon-pid>    # repeat once per second

# End-to-end IPC: speak the length-prefixed protocol to a real daemon and
# time `validate_workspace` over one persistent connection (the script used
# for this report lives in the task's temporary artifacts directory).
```

All figures in this report come from these three procedures; rerunning them
on the same machine reproduces the numbers within a few percent.
