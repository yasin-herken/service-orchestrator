# Task 025 — Performance & Resource Optimization

## Role

Act as a Principal Rust Performance Engineer, Systems Architect, Tokio Concurrency Specialist, React Performance Engineer, and macOS Developer Tooling Engineer.

You are implementing **Task 025 — Performance & Resource Optimization** of the Service Orchestrator project.

Your objective is to measure, analyze, and optimize the performance and resource efficiency of the existing application.

This is a single, end-to-end engineering task.

Do not stop after planning. Inspect, benchmark, optimize, test, document, and report the completed work.

Follow these rules throughout the task:

# 4. Performance Principles

Follow a measurement-driven optimization approach.

```text
Measure
   |
   v
Identify Bottleneck
   |
   v
Form Hypothesis
   |
   v
Implement Targeted Change
   |
   v
Measure Again
   |
   v
Verify Correctness
```

Do not optimize code solely because it appears inefficient.

Do not sacrifice correctness or safety for small performance improvements.

# 13. Scheduler Concurrency

Verify configured concurrency limits.

Example:

```toml
[execution]
max_parallel_tasks = 4
```

Ensure the scheduler:

- Respects concurrency limits
- Avoids starvation
- Does not create unnecessary workers
- Does not hold locks during long-running operations
- Handles cancellation efficiently

Do not increase concurrency blindly.

---

# 14. Lock Contention

Inspect shared synchronization primitives.

Look for:

- Long-held mutex guards
- Locks held across `.await`
- Excessive global locking
- Nested locks
- Contention between independent services

Prefer narrower lock scopes.

Do not replace safe synchronization with unsafe code merely for performance.

---

# 15. Workflow Planning Performance

Measure dependency graph operations.

Test:

- Dependency closure
- Topological ordering
- Cycle detection
- Workflow plan generation
- Profile resolution
- Group resolution

Avoid repeatedly reconstructing unchanged graphs when measurable benefits justify caching.

Ensure cache invalidation respects configuration changes.

---

# 16. IPC Performance

Measure Unix Domain Socket communication.

Evaluate:

- Request latency
- Response serialization
- Message framing
- Concurrent requests
- Event delivery
- Connection overhead
- Large response handling

Do not replace the IPC protocol without evidence of a meaningful bottleneck.

---

# 17. IPC Payload Optimization

Inspect payload sizes.

Avoid:

- Returning entire workspace state for small queries
- Sending unbounded logs
- Repeatedly serializing unchanged data
- Sending redundant fields
- Large event payloads

Introduce targeted pagination or compact responses where appropriate.

Preserve protocol compatibility where possible.

---

# 18. IPC Event Streaming

Measure event delivery under load.

Test:

- Multiple clients
- Frequent task events
- Continuous logs
- Slow subscribers
- Client disconnects

Use bounded channels and explicit backpressure policies.

Do not allow one slow client to block the daemon.

---

# 19. Git Status Performance

Measure repository status collection.

For a workspace containing many repositories, avoid unnecessary repeated Git commands.

Consider:

- On-demand refresh
- Bounded parallel status collection
- Short-lived status caching
- Event-driven invalidation where practical

Do not continuously scan all repositories without a reason.

Do not return stale Git state as current without indicating freshness.

---

# 20. Process Manager Performance

# 23. Log Retention

- In-memory buffers are bounded.
- Historical queries are paginated.

Do not silently delete logs outside documented retention policies.
