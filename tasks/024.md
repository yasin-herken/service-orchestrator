# Task 024 — Desktop UX & Cross-Interface Consistency# Task 024 — Desktop UX & Cross-Interface Consistency

## Role

Act as a Principal Rust Engineer, Senior Tauri 2 Engineer, React/TypeScript Architect, macOS Desktop UX Engineer, and Distributed Systems Reliability Engineer.

You are implementing **Task 024 — Desktop UX & Cross-Interface Consistency** of the Service Orchestrator project.

Your objective is to improve the quality, consistency, reliability, and usability of the existing desktop application and ensure all interfaces operate against the same authoritative application state.

This is a single, end-to-end implementation task.

Do not stop after planning. Inspect, implement, test, fix, document, and report the completed work.

---

# 1. Execution Strategy

Follow these rules:

- Read `AGENTS.md` completely.
- Read only documentation relevant to the affected modules.
- Inspect the existing implementation before introducing abstractions.
- Reuse existing Application Core, IPC, daemon, Tauri, React, TUI, and MCP components.
- Avoid repeatedly analyzing unrelated modules.
- Do not redesign working architecture.
- Do not create duplicate business logic.
- Run focused tests during implementation.
- Run full validation at completion.
- Maintain a concise progress record in `docs/task-025-progress.md` if useful for context recovery.
- Request approval only for genuinely destructive, sensitive, or externally impactful operations.

Complete the entire task whenever technically possible.

Do not stop after producing an implementation plan.

---

# 2. Project Context

Service Orchestrator is a local macOS developer orchestration platform.

Existing interfaces:

- Tauri 2 + React + TypeScript desktop GUI
- Ratatui TUI
- MCP server for AI agents

All interfaces must communicate with the same local daemon.

The daemon owns:

- Application Core
- Task Engine
- Workflow Engine
- Process Manager
- Service Runtime
- Git Manager
- Build Manager
- Library Manager
- Migration Manager
- Health Manager
- Observability
- Policy Engine

The application must work without an LLM.

---

# 3. Primary Goal

Improve the existing product in five areas:

1. Desktop UX consistency
2. Cross-interface state consistency
3. Realtime event reliability
4. Error handling and recovery
5. Navigation and interaction quality

Do not introduce unrelated product features.

---

# 4. Architecture

Preserve:

```text
Tauri GUI ────┐
              │
Ratatui TUI ──┼──► Local IPC ──► Shared Daemon
              │                      │
MCP Server ───┘                      ▼
                              Application Core
                                    │
                              Task Engine
                                    │
                              Infrastructure
```

The daemon must remain the authoritative source of truth.

Clients may cache data for rendering but must never maintain competing authoritative state.

---

Inspect all existing desktop screens:

- Dashboard
- Services

- Inconsistent confirmation dialogs

Fix confirmed issues.

Do not redesign screens that already work well.

# 7. macOS Desktop Experience

Improve the application to feel natural on macOS.

Consider:

- Minimum window dimensions
- Native-feeling navigation
- Keyboard shortcuts
- Focus management
- Dark/light theme behavior
- Dialog interactions
- Scroll behavior
- Sidebar behavior

---

# 8. Navigation

Review the desktop navigation structure.

Ensure:

- All implemented screens are reachable.
- Active navigation is visible.
- Navigation preserves appropriate state.
- Back navigation behaves predictably.
- Workspace switching is consistent.
- Deep links between related records work.

Do not create unnecessary navigation layers.

---

# 9. Keyboard Accessibility

Support keyboard-first workflows where practical.

Examples:

- Navigate services
- Search
- Select multiple services
- Open details
- Close dialogs
- Trigger supported actions
- Navigate task results
- Navigate logs

Avoid shortcut collisions.

Do not override standard text input shortcuts.

---

# 10. Service Selection Consistency

Ensure service selection behaves consistently across:

- Services
- Git
- Builds
- Workflows

Use stable workspace-aware identifiers.

Selection must not accidentally include hidden or unrelated services.

Clearly distinguish:

- Selected items
- Filtered items
- All workspace items

Do not use array indices as identity.

---

# 11. Bulk Operation UX

Improve bulk operation interactions.

For each bulk operation, clearly display:

- Selected resources
- Operation type
- Expected effects
- Warnings
- Authorization requirements
- Progress
- Final results

Do not execute unexpected operations on unselected resources.

---

# 12. Status Representation

Standardize visual representation of:

- Running
- Starting
- Stopping
- Stopped
- Failed
- Unknown
- Healthy
- Unhealthy
- Degraded
- Queued
- Cancelled
- Blocked

Keep runtime, health, and task status conceptually separate.

Do not rely only on colors.

---

# 13. Loading States

Every asynchronous screen should provide appropriate loading feedback.

Avoid:

- Empty screens during loading
- Infinite spinners
- Misleading stale data
- Blocking the entire application unnecessarily

Use existing query/loading infrastructure.

---

# 14. Empty States

Provide meaningful empty states.

Examples:

- No configured services
- No running tasks
- No recent logs
- No configured profiles
- No migration-enabled services
- No health history

Do not display fake placeholder data as real data.

Since service configuration editing is deferred, empty states may direct users to the existing configuration documentation rather than a nonexistent Add Service action.

---

# 15. Error UX

Standardize error presentation.

Errors should include:

- Affected resource
- Operation
- Reason
- Suggested next action
- Related Task ID where available

Do not expose raw internal stack traces.

Do not hide useful structured errors.

---

# 16. Notifications

Implement or improve a consistent notification system.

Support:

- Operation accepted
- Operation completed
- Operation failed
- Connection lost
- Connection restored
- Authorization required

Avoid excessive notifications for routine background events.

---

# 17. Confirmation Dialogs

Standardize confirmation behavior.

Use confirmation dialogs for appropriate mutating or sensitive operations.

Display:

- Operation
- Affected resources
- Consequences
- Authorization requirements

Frontend confirmation must not bypass daemon policy enforcement.

---

# 18. Cross-Interface State Consistency

Verify that GUI, TUI, and MCP observe the same authoritative state.

Important resources:

- Services
- Processes
- Tasks
- Workflows
- Health
- Logs
- Git operations
- Build operations
- Library operations
- Migrations

Do not assume event delivery alone guarantees consistency.

---

# 19. State Synchronization

Use a reliable state synchronization strategy.

Prefer:

1. Initial authoritative snapshot
2. Realtime event updates
3. Reconciliation after reconnect
4. Targeted refresh when events are missed

Do not continuously reload the entire workspace without justification.

---

# 20. Event Ordering

Inspect event ordering behavior.

Potential issues:

- Old events overwriting newer state
- Duplicate events
- Missed events
- Events arriving after workspace switching
- Task completion arriving before a progress update
- Reconnection causing duplicate subscriptions

Use event sequence numbers or revision information where supported.

If unavailable, implement the smallest reliable reconciliation mechanism.

---

# 21. Realtime Event Reliability

Verify:

- Task events
- Workflow events
- Service runtime events
- Health events
- Log events
- Daemon connection events

Ensure event subscriptions are cleaned up correctly.

Avoid memory leaks.

---

# 22. Daemon Reconnection

Improve client reconnection behavior.

When connection is lost:

- Display disconnected state.
- Disable unsafe mutating actions.
- Preserve safe UI state.
- Attempt controlled reconnection.
- Reload authoritative state.
- Restore subscriptions.
- Avoid duplicate execution.

Do not automatically replay uncertain mutating operations.

---

# 23. Duplicate Operation Protection

Verify that repeated user actions cannot create duplicate operations.

Examples:

- Start service repeatedly
- Restart service repeatedly
- Submit same build repeatedly
- Execute same workflow repeatedly

Frontend pending-state protection is useful but insufficient.

The daemon must remain responsible for operation coordination.

---

# 24. Task Consistency

Verify:

- Task IDs are stable.
- Task status is authoritative.
- Progress updates are consistent.
- Cancellation is reflected across interfaces.
- Terminal states are not overwritten by stale events.
- Task results are available to all clients.

Do not introduce a second task registry.

---

# 25. Workflow Consistency

Verify:

- Workflow IDs are stable.
- Workflow phases are consistent.
- Task relationships are preserved.
- Partial failures are represented accurately.
- Cancellation state is shared.
- Reconnection restores workflow state.

Do not recreate workflow state from frontend-only assumptions.

---

# 26. Process Consistency

Verify:

- GUI-started services appear in TUI.
- MCP-started services appear in GUI.
- TUI-stopped services appear stopped in MCP.
- Process ownership remains with the daemon.
- No interface directly owns managed service processes.

Do not terminate unrelated processes.

---

# 27. Health Consistency

Verify health state is consistent across interfaces.

Do not confuse:

- Process liveness
- TCP reachability
- HTTP health
- Application readiness

A running process may still be unhealthy.

---

# 28. Log Consistency

Verify:

- Service logs are associated with correct services.
- Task logs are associated with correct tasks.
- Workflow logs are correlated correctly.
- Log pagination is stable.
- Realtime log subscriptions do not duplicate entries.
- Slow consumers do not block producers.

Do not introduce a second log storage system.

---

# 29. Workspace Switching

Verify workspace switching across desktop screens.

Requirements:

- Correct workspace scoping
- Correct service selection
- Correct task filtering
- Correct workflow filtering
- Correct log subscriptions
- No stale response overwrites
- No cross-workspace data mixing

---

# 30. IPC Reliability

Review the existing IPC client integration.

Test:

- Concurrent requests
- Request timeouts
- Connection loss
- Reconnection
- Protocol errors
- Invalid responses
- Event stream interruptions
- Slow consumers

Do not rewrite the IPC protocol unless a confirmed defect requires it.

---

# 31. MCP Consistency

Verify MCP tools return the same authoritative state as TUI and GUI.

Do not introduce MCP-specific business logic.

Ensure structured errors remain consistent.

Do not change existing MCP tool names or schemas unnecessarily.

---

# 32. TUI Consistency

Verify TUI remains functional after desktop improvements.

Focus on:

- Service state
- Task progress
- Workflow progress
- Health status
- Logs
- Reconnection
- Error handling

Do not redesign the entire TUI.

---

# 33. Desktop Performance

Inspect and improve:

- Duplicate IPC requests
- Unnecessary full-list refreshes
- Expensive filtering
- Large log rendering
- Unbounded event listeners
- Memory growth

Optimize confirmed bottlenecks.

Improve:

- Accessible labels

- Non-color status indicators

Preserve existing visual design where possible.
