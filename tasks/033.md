# Task 033 — Workspace Control Center: Unified Single-Screen Developer Operations

## Role

Act as a Principal Rust Engineer, Senior Tauri 2 Engineer, React/TypeScript Architect, and Developer Productivity UX Engineer.

Implement **Task 033 — Workspace Control Center** in the existing Service Orchestrator application.

The primary goal is to minimize user interactions.

A developer must be able to select services, configure operations, execute them, monitor progress, and inspect results without navigating away from a single desktop screen.

This is a complete implementation task, not a design proposal.

## 1. Execution Strategy

- Read `AGENTS.md`.
- Inspect the existing Tauri GUI, Application Core, daemon IPC, workflows, service templates, and operation presets.
- Reuse existing functionality.
- Do not create another workflow engine, scheduler, process manager, or configuration system.
- Avoid unnecessary architectural refactoring.
- Implement, test, fix, and document the feature end-to-end.
- Run focused tests during development and full validation at completion.
- Do not stop after planning.
- Request authorization for genuinely destructive or sensitive operations.

## 2. Product Principle

**One screen. One selection. One execution.**

The current application contains multiple management tabs.

Keep all existing tabs intact.

Add a new primary tab named:

**Workspace Control Center**

Make it the default landing screen.

The existing screens remain available for advanced management.

Users must not be required to navigate to Git, Build, Libraries, Migrations, Workflows, or Templates to perform routine operations.

## 3. Screen Layout

Design a clean, compact macOS desktop interface containing:

1. Workspace selector
2. Service selection
3. Operations configuration
4. Advanced options
5. Plan preview
6. Execute button
7. Realtime progress
8. Results and logs

Use the existing design system.

Avoid large multi-step wizards.

## 4. Service Selection Modal

Provide a service selection modal.

Support:

- Search
- Filter by backend/frontend/library
- Select all
- Select visible
- Clear selection
- Profile selection
- Group selection
- Multi-selection

Display service name, type, current branch, runtime status, and health where available.

Preserve selection while navigating or filtering.

Use stable workspace-aware identifiers.

## 5. Operation Selection

Display the following operations directly on the main screen:

- Git Sync
- Build & Install Libraries
- Liquibase
- Build Services
- Start Services
- Stop Services
- Restart Services
- Health Checks

Use checkboxes, switches, dropdowns, and compact inline controls.

Show only relevant options for enabled operations.

Do not require navigating to separate tabs.

## 6. Git Controls

When Git Sync is enabled, show:

- Target branch
- Fetch
- Checkout
- Fast-forward pull

Default branch should come from configuration.

Allow overriding it directly.

Preserve uncommitted changes.

Do not perform destructive Git operations automatically.

## 7. Library Controls

Support:

- Build required libraries
- Install locally
- Verify artifacts
- Inspect version alignment

Use existing Library Manager capabilities.

## 8. Liquibase Controls

Support named migration presets:

- Status
- Update
- Reset Local Database + Update

Support configured contexts.

For example:

```bash
mvn liquibase:dropAll liquibase:update -Dliquibase.contexts=sql,data,onlyDev
```

Use structured execution arguments.

Do not implement unrestricted shell command execution.

Destructive database reset must require verified database targets and trusted authorization.

Do not assume localhost is safe.

Do not automatically retry destructive migrations.

## 9. Build Controls

Support:

- Build
- Clean install where supported
- Install dependencies
- Skip tests where supported

Use existing BuildProvider capabilities.

Do not hard-code Maven behavior into the UI.

## 10. Runtime Controls

Support:

- Start
- Stop
- Restart
- Wait for readiness

Do not permit conflicting runtime actions in the same workflow unless the backend explicitly supports their sequencing.

Use existing Service Runtime and workflow operations.

## 11. Templates as Defaults

Templates must provide configuration defaults, not mandatory daily workflow steps.

When a service already has valid configuration, use it directly.

Users must not be forced to create a template before executing an operation.

Advanced template-related settings may be edited through a modal or drawer.

Do not duplicate template configuration inside the Control Center.

## 12. Advanced Settings

Provide a compact Advanced Settings modal or drawer.

Include relevant service-specific overrides such as:

- Working directory
- Build operation
- Runtime command
- Migration preset
- Health check
- Timeout
- Environment references

Use validated existing configuration and request models.

Do not silently persist temporary overrides as permanent service configuration.

## 13. Read-Only Planning

Before execution, generate a real backend workflow plan.

Display:

- Selected services
- Resolved dependencies
- Required libraries
- Git operations
- Migration operations
- Build operations
- Runtime operations
- Health checks
- Warnings
- Authorization requirements

Planning must not modify repositories, databases, or running processes.

## 14. One-Click Execution

Provide one primary action:

**Prepare & Run**

This must submit one coordinated workflow through the existing Application Core and shared daemon.

Do not implement a series of independent frontend requests.

One-click execution must not bypass required authorization.

For ordinary authorized operations, minimize unnecessary confirmation dialogs.

For destructive operations, require appropriate trusted authorization.

## 15. Progress on the Same Screen

After execution, show realtime progress directly within the Control Center.

Display:

- Workflow ID
- Current phase
- Completed tasks
- Running tasks
- Pending tasks
- Failed tasks
- Blocked tasks
- Per-service status

Do not navigate automatically to the Tasks screen.

Allow expanding individual tasks and logs inline or in a modal.

## 16. Results on the Same Screen

Display an aggregated result after completion.

Include:

- Overall status
- Per-service results
- Failed operations
- Blocked operations
- Relevant error messages
- Task IDs
- Final runtime and health states

Support viewing detailed logs without leaving the Control Center.

## 17. Quick Actions

Provide convenient actions for selected services:

- Git Sync Only
- Build Only
- Start Only
- Stop Only
- Restart Only
- Health Check Only
- Full Prepare Environment

These actions must reuse existing Application Core operations.

Do not create duplicate execution logic.

## 18. Saved Selections

Remember the last selected workspace, services, and operation options where appropriate.

Use existing preferences or preset storage.

Do not store secrets.

Loading saved preferences must not execute operations automatically.

Do not persist destructive-operation authorization.

## 19. Error Handling

Display actionable errors on the same screen.

Examples:

- Dirty repository
- Missing branch
- Maven unavailable
- Node version mismatch
- Liquibase target unauthorized
- Port conflict
- Build failure
- Health timeout
- Daemon disconnected

Do not force users to navigate elsewhere to understand routine failures.

## 20. Daemon Integration

Use the existing architecture:

React → Typed Desktop API → Tauri Commands → IPC → Shared Daemon → Application Core.

The daemon remains authoritative.

Do not introduce new process ownership or task state.

## 21. Reconnection

When daemon connection is lost:

- Display connection status.
- Disable mutating actions.
- Preserve current selection.
- Attempt safe reconnection.
- Restore workflow state.
- Reestablish event subscriptions.

Do not automatically replay uncertain mutating operations.

## 22. Performance

The screen must remain responsive with:

- 40 configured repositories
- 100+ services
- Multiple active tasks
- Continuous logs
- Frequent runtime events

Avoid excessive rerenders and duplicate IPC requests.

## 23. Tests

Add frontend tests for:

- Service selection modal
- Filtering
- Multi-selection
- Operation toggles
- Git branch overrides
- Liquibase preset selection
- Advanced settings
- Workflow planning
- Workflow execution
- Progress
- Cancellation
- Results
- Quick actions
- Reconnection

Add Rust adapter and integration tests where required.

Use fixture repositories and databases.

Run applicable checks:

Run available frontend checks:

