# Goal

Implement the **Application Core and Use Case layer**.

This layer is the central application API used by all interfaces.

The critical architectural rule is:

> TUI and MCP must call the same application use cases. Neither interface may contain business orchestration logic.

At the end of this task, we should have a clean application-level API that later can be used by:

```text
Ratatui
MCP
CLI
Future GUI
Future API
```

without duplicating business logic.

---

# 1. Architecture

The desired structure is:

```text
                   ┌──────────────┐
                   │    Ratatui   │
                   └──────┬───────┘
                          │
                   ┌──────▼───────┐
                   │ Application  │
                   │    Core      │
                   └──────┬───────┘
                          │
                   ┌──────▼───────┐
                   │    Domain    │
                   └──────────────┘


                   ┌──────────────┐
                   │ MCP Adapter  │
                   └──────┬───────┘
                          │
                   ┌──────▼───────┐
                   │ Application  │
                   │    Core      │
                   └──────────────┘
```

The application crate should depend on domain contracts and infrastructure abstractions.

It must NOT depend on:

- `ratatui`
- `rmcp`
- TUI-specific types
- MCP-specific types

# 3. Commands and Queries

Separate write/action operations from read operations where practical.

For example:

```text
Queries
-------
ListServices
GetService
GetServiceStatus
GetWorkspaceStatus
GetTask
GetLogs


Commands
--------
SyncService
BuildService
BuildLibrary
RunLiquibase
StartService
StopService
RestartService
PrepareEnvironment
StartProfile
StopProfile
CancelTask
```

The exact naming can be improved if there is a clear reason.

Avoid introducing unnecessary CQRS complexity.

This is logical separation, not a requirement to create a distributed CQRS system.

---

# 4. Application Context

Introduce a clean application context/service container where appropriate.

Conceptually:

```rust
pub struct Application {
    ...
}
```

It should contain or reference application-level dependencies such as:

```text
Configuration
Task Engine abstraction
Git abstraction
Build abstraction
Process abstraction
Health abstraction
Logging abstraction
Policy abstraction
```

However:

IMPORTANT:

Do not implement all infrastructure components yet.

Use traits/interfaces or placeholder implementations only where necessary to define the boundary.

Avoid speculative dependency injection frameworks.

Use straightforward Rust composition.

---

# 5. Infrastructure Boundaries

Define the interfaces that the application layer needs.

Potential boundaries:

```rust
trait GitService
trait BuildService
trait ProcessService
trait LiquibaseService
trait HealthService
trait LogService
trait TaskService
trait PolicyService
```

Do not blindly create one trait for every noun.

Create an abstraction only when the application layer needs to communicate with an external subsystem or when it provides a real architectural boundary.

Document important decisions.

---

# 6. Repository / Service Access

The application layer should not directly parse configuration files.

Configuration should already be loaded by the configuration system.

The application should work with validated configuration/domain objects.

Conceptually:

```text
Config Loader
     ↓
Validated Configuration
     ↓
Application
     ↓
Use Cases
```

Avoid patterns such as:

```rust
use_case -> read config.toml -> parse service
```

---

# 7. Application State

Determine which state belongs to:

### Persistent state

Examples:

```text
Configuration
Workspace definition
Service definition
Profiles
Groups
```

### Runtime state

Examples:

```text
Running services
Active processes
Tasks
Task progress
Health state
Current Git state
```

Do not mix persistent configuration with transient runtime state.

Document the distinction.

---

# 8. Service Queries

Implement application-level queries such as:

```text
list_services(workspace)
get_service(service_id)
get_service_status(service_id)
get_workspace_status(workspace_id)
```

Return structured application/domain data.

Do not return formatted TUI strings.

Bad:

```text
"auth-service - RUNNING - :8081"
```

Good:

```rust
ServiceStatus {
    service_id,
    process_state,
    health_state,
    git_state,
    branch,
    port,
}
```

The TUI and MCP can format this independently.

---

# 9. Command Execution Contracts

Commands should return structured results.

For example:

```rust
pub struct OperationResult {
    pub task_id: TaskId,
    pub accepted: bool,
}
```

Long-running operations should normally return a task identifier rather than blocking indefinitely.

Example:

```text
start_service
      ↓
TaskId
      ↓
task engine
```

---

# 10. Task Integration Boundary

The application layer must be prepared to work with the future Task Engine.

Do not implement the scheduler in this task.

Define the minimum contract required by the application layer.

For example, conceptually:

```rust
trait TaskManager {
    fn submit(&self, task: TaskDefinition) -> Result<TaskId>;
    fn get(&self, task_id: TaskId) -> Result<TaskStatus>;
    fn cancel(&self, task_id: TaskId) -> Result<()>;
}
```

The exact API may differ.

The important thing is:

> Application use cases request work. The Task Engine executes work.

---

# 11. Workflow Boundary

Define the application-level representation of workflows.

For example:

```text
PrepareEnvironment
StartProfile
SyncWorkspace
BuildWorkspace
```

Application use cases should be able to construct workflow/task definitions without directly executing commands.

Conceptually:

```text
PrepareEnvironment
       ↓
Workflow Definition
       ↓
Task Manager
```

Do not implement workflow scheduling yet.

---

# 12. Dependency Handling

The application layer should be able to validate referenced services/libraries before creating operations.

Example:

```text
Start user-service
      ↓
requires auth-service
      ↓
requires common-core
```

At this stage:

- Validate that references exist.
- Preserve dependency information.
- Do not implement full dependency-aware scheduling yet.

---

# 13. Policy Integration

Application commands that can mutate the workspace must pass through a policy boundary.

Example:

```text
StartService
     ↓
Policy Check
     ↓
Task submission
```

Destructive actions must be clearly classified.

Examples:

```text
Read
SafeWrite
Destructive
```

Do not bypass policy checks just because the caller is trusted.

Both TUI and MCP will eventually use the same application API.

---

# 14. Error Handling

Application errors should be meaningful and independent of interface concerns.

For example:

```text
ServiceNotFound
WorkspaceNotFound
LibraryNotFound
InvalidOperation
TaskNotFound
PermissionDenied
DependencyNotFound
ConfigurationInvalid
WorkflowInvalid
```

Infrastructure errors should retain their context without leaking low-level implementation details unnecessarily.

Do not create an enormous catch-all error type.

---

# 15. Result Design

Application results must be machine-readable.

Examples:

```rust
ServiceStatus
WorkspaceStatus
OperationAccepted
TaskStatus
OperationResult
```

Do not return:

```text
String
Vec<String>
```

just because they are easy to render.

Structured types should be used whenever the result represents application state.

---

# 16. Read Operations Must Be Side-Effect Free

Query operations should not unexpectedly mutate the workspace.

For example:

```text
get_service_status
```

must not:

- checkout branches
- fetch repositories
- build services
- start processes

unless explicitly documented.

Keep reads predictable.

---

# 17. Command Idempotency

Where appropriate, application commands should be designed with idempotency in mind.

Examples:

```text
Start an already-running service
```

should produce a predictable result instead of blindly creating another process.

Similarly:

```text
Stop an already-stopped service
```

should be handled gracefully.

Document the chosen behavior.

---

# 18. Operation Preconditions

Application use cases should validate basic preconditions before task creation.

Examples:

### StartService

Check:

- Service exists
- Workspace exists
- Configuration is valid
- Required runtime configuration exists
- Service is not already running
- Required dependencies are resolvable

### BuildService

Check:

- Service exists
- Build command is configured
- Workspace path is valid

### RunLiquibase

Check:

- Service exists
- Liquibase is enabled
- Liquibase command exists

Do not perform the actual execution yet.

# 19. Application API

Create a clean high-level API.

Possible conceptual interface:

```rust
pub trait ServiceOrchestrator {
    fn list_services(&self, workspace_id: &WorkspaceId) -> Result<Vec<Service>>;
    fn get_service_status(&self, service_id: &ServiceId) -> Result<ServiceStatus>;

    fn sync_service(&self, service_id: &ServiceId) -> Result<OperationAccepted>;
    fn build_service(&self, service_id: &ServiceId) -> Result<OperationAccepted>;

    fn start_service(&self, service_id: &ServiceId) -> Result<OperationAccepted>;
    fn stop_service(&self, service_id: &ServiceId) -> Result<OperationAccepted>;
    fn restart_service(&self, service_id: &ServiceId) -> Result<OperationAccepted>;

    fn prepare_environment(
        &self,
        request: PrepareEnvironmentRequest,
    ) -> Result<OperationAccepted>;
}
```

The exact API may be implemented differently.

Prefer concrete application services where appropriate rather than forcing every operation behind one giant trait.

---

# 20. Request Objects

For complex operations, use explicit request objects.

Example:

```rust
pub struct PrepareEnvironmentRequest {
    pub workspace_id: WorkspaceId,
    pub services: Vec<ServiceId>,
    pub branch: Option<String>,
    pub run_liquibase: bool,
    pub build: bool,
    pub start: bool,
}
```

Avoid huge positional argument lists.

Request objects also make MCP mapping easier later.

---

# 21. TUI Independence

The application layer must NOT know that Ratatui exists.

Do not add:

```rust
use ratatui::...
```

to application/domain crates.

Do not return:

```text
TableRow
ListItem
Color
Span
Widget
```

from application code.

---

# 22. MCP Independence

The application layer must NOT know that MCP exists.

Do not add:

```rust
use rmcp::...
```

to application/domain crates.

Do not return MCP-specific response types from application use cases.

MCP-specific serialization belongs in the MCP adapter.

Enforce the intended dependency direction:

```text
             ┌──────────┐
             │   TUI    │
             └────┬─────┘
                  │
             ┌────▼─────┐
             │  MCP     │
             └────┬─────┘
                  │
                  ▼
          ┌───────────────┐
          │ Application   │
          └───────┬───────┘
                  │
                  ▼
             ┌────────┐
             │ Domain │
             └────────┘
```

Infrastructure implementations should be plugged into application boundaries.

Do not make domain depend on infrastructure.

# 25. Avoid Speculative Ports

Do not create interfaces solely because they might be useful someday.

For each port/trait, ask:

> Does the application layer currently need this boundary?

If not, avoid adding it.

The architecture should be extensible without becoming abstract for abstraction's sake.

---

# 26. Dependency Injection

Use simple dependency injection through constructors or structs.

Example:

```rust
Application::new(
    config,
    task_manager,
    git_service,
    build_service,
    process_service,
)
```

Avoid introducing a dependency injection framework.

Rust's type system and explicit composition are sufficient.

---

# 27. Runtime State Store

If runtime state needs a temporary store, introduce a focused abstraction.

Possible data:

```text
Service runtime state
Task state
Process information
Health state
```

Do not introduce a database.

For the MVP, in-memory runtime state is expected.

Document the decision.

---

# 28. Workspace Scope

All application operations should be workspace-aware.

Avoid assuming there is only one workspace.

For example:

```text
start_service(workspace_id, service_id)
```

or another model that guarantees unambiguous service resolution.

Do not depend solely on global service names if multiple workspaces can coexist.

---

# 29. Logging Boundary

Application code should log meaningful events but must not depend directly on a concrete logging backend unless necessary.

Use the project's chosen logging abstraction.

Do not expose secrets.

Do not log entire environment maps.

---

# 30. Observability

Application operations should produce enough information for later interfaces to answer:

- What happened?
- Which service?
- Which task?
- When?
- Why did it fail?

Do not rely on parsing logs as the only source of state.

Create unit tests for the application layer.

Test at least:

### Queries

- Service listing
- Unknown service
- Workspace status

### Commands

- Start service preconditions
- Stop service preconditions
- Build validation
- Liquibase validation
- Unknown service
- Invalid workspace

### Policy

- Read operation allowed
- Safe write allowed
- Destructive operation rejected/blocked without required authorization

### Task submission

Verify that commands submit the expected task definitions to the Task Manager abstraction.

Use mocks/fakes at infrastructure boundaries.

Do not run real Maven/Git/process commands in these unit tests.
