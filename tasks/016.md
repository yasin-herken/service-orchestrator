# 2. Primary Goal

Implement a high-level **Prepare Development Environment** workflow.

A developer must be able to select services and execute a complete development environment preparation process.

The workflow must support:

1. Workspace validation
2. Service selection
3. Dependency resolution
4. Git synchronization
5. Library preparation
6. Database migrations
7. Service builds
8. Service startup
9. Health/readiness checks
10. Aggregated execution results

The workflow must be accessible through the existing Application Core.

TUI and MCP must use the same implementation.

---

# 3. Architectural Principle

The Application Core defines the workflow.

The Task Engine schedules and executes tasks.

Existing managers perform infrastructure operations.

The daemon owns the authoritative runtime state.

TUI and MCP remain thin adapters.

```text
TUI / MCP
    |
    v
Shared Local Daemon
    |
    v
Application Core
    |
    v
Workflow Orchestrator
    |
    v
Task Engine / Scheduler
    |
    +---- Git Manager
    +---- Library Manager
    +---- Migration Manager
    +---- Build Manager
    +---- Service Runtime
    +---- Health Manager
    |
    v
Structured Workflow Result
```

Do not implement a second scheduler.

Do not duplicate Git, build, migration, or runtime logic.

# 13. Local Changes Safety

Never silently discard local changes.

If a repository cannot safely switch branches or pull:

- Mark the repository operation as blocked or failed.
- Preserve local changes.
- Provide an actionable reason.
- Prevent unsafe dependent operations.
- Continue independent work according to the workflow failure policy.

Do not automatically stash, reset, clean, or force checkout.

# 15. Library Preparation

Use the existing Library Manager.

Required behavior:

1. Resolve required libraries.
2. Determine dependency order.
3. Build libraries using configured BuildProviders.
4. Install local artifacts where supported.
5. Verify artifacts.
6. Check dependent service version alignment.

Do not assume installing an artifact automatically changes a consumer's dependency version.

A version mismatch must be reported explicitly.

Do not silently rewrite Maven POM files.

---

# 16. Library Development Mode

Support preparing services against locally modified libraries.

If Git synchronization is disabled, the workflow should be able to build a library from its current local branch.

Do not force every library to checkout `master`.

Preserve uncommitted developer changes.

---

# 17. Migration Integration

Use the existing Migration Manager.

Only migration-enabled services should receive migration tasks.

Disabled migrations should be skipped explicitly.

Respect:

- Database target safety
- Authorization
- Database-scoped operation coordination
- Migration timeouts
- Failure propagation
- No automatic retry after partial failure

Do not treat migrations as harmless build operations.

---

# 18. Migration Failure

If a required migration fails:

- Mark the migration task as failed.
- Block dependent startup steps.
- Preserve relevant diagnostics.
- Do not claim the database was rolled back.
- Continue unrelated services only when safe.

Do not automatically rerun failed migrations.

# 23. Concurrency

Reuse the existing Task Engine Scheduler.

Respect:

```toml
[execution]
max_parallel_tasks = 4
```

Do not create a separate workflow scheduler.

Independent tasks may execute concurrently.

Dependent tasks must wait.

Database migration locks and repository operation locks must remain effective.

---

# 24. Failure Policies

Define explicit workflow failure behavior.

At minimum support a safe default:

- Required dependency failure blocks dependent tasks.
- Independent tasks may continue.
- Failed tasks retain structured results.
- The workflow reports partial success accurately.

Do not automatically roll back completed Git, build, or migration operations.

These operations are not generally transactional.

---

# 25. Cancellation

Support cancelling the entire workflow.

Cancellation must:

1. Stop scheduling pending tasks.
2. Cancel running tasks where supported.
3. Propagate cancellation to external processes.
4. Prevent dependent tasks from starting.
5. Preserve completed task results.
6. Report partial completion accurately.

Do not automatically stop services that were already running before the workflow.

For services started by the workflow, define and document the cleanup policy.

Avoid destructive cleanup by default.

# 35. Authorization

All workflow steps must respect the shared policy engine.

Planning must identify operations requiring authorization.

Execution must enforce authorization again.

Do not trust a plan merely because it was generated earlier.

Do not accept an arbitrary `confirmed: true` flag as authorization.

Use the trusted authorization mechanism established in earlier tasks.

# 36. Plan Freshness

A workflow plan may become stale.

For example:

- Git state changes.
- Another process occupies a port.
- A service starts.
- Configuration changes.
- Database migration state changes.

Revalidate important preconditions immediately before execution.

Do not assume a previously generated plan remains valid indefinitely.

---

# 37. Idempotency

Design workflows to behave predictably when repeated.

Examples:

- Already-running service
- Already-installed library
- Already-up-to-date repository
- Already-applied Liquibase changesets

Do not assume every operation is safely repeatable.

Avoid unnecessary work where reliable state checks are available.

---

# 38. Operation Coordination

Preserve existing operation locks.

Examples:

- Repository-level Git locks
- Service-level start/stop coordination
- Library artifact coordination
- Database-target migration coordination

Do not introduce a global lock that blocks all independent operations.
