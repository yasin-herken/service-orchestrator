# Goal

Implement the **Task Engine and Scheduler**.

This is one of the most important components of Service Orchestrator.

The Task Engine is responsible for executing long-running developer operations such as:

- Git operations
- Maven builds
- npm operations
- Liquibase migrations
- Starting/stopping processes
- Health checks
- Multi-service workflows

The Task Engine must be independent from:

- Ratatui
- MCP
- Git implementation
- Maven implementation
- Node implementation
- OS-specific UI behavior

The Task Engine should provide a generic execution model that can be reused by TUI, MCP, CLI, and future interfaces.

---

# 1. Core Principle

The application layer creates tasks.

The Task Engine executes tasks.

The infrastructure layer performs the actual operation.

The interface only observes and controls task state.

The intended flow is:

```text
TUI ─────┐
         │
MCP ─────┼──> Application Use Case
         │
CLI ─────┘
              ↓
        Task Definition
              ↓
         Task Engine
              ↓
          Scheduler
              ↓
      Task Executor / Handler
              ↓
         Infrastructure
```

Do NOT put business workflow logic inside the scheduler.

Do NOT put UI logic inside the scheduler.

---

# 2. Responsibilities

The Task Engine must provide:

- Task creation
- Task identification
- Task submission
- Task scheduling
- Dependency handling
- Concurrency control
- State transitions
- Progress reporting
- Task cancellation
- Retry support
- Timeout handling
- Failure propagation
- Task result storage
- Task history
- Task querying

---

# 3. Task Lifecycle

Support these task states:

```text id="mwz5j4"
Queued
Running
Succeeded
Failed
Cancelled
Skipped
Blocked
```

A valid state transition model must be defined.

Example:

```text id="0jht7w"
Queued
   │
   ▼
Running
   ├──> Succeeded
   ├──> Failed
   └──> Cancelled
```

Dependency failures may produce:

```text id="eyz7u7"
Blocked
Skipped
```

depending on the workflow policy.

Do not allow invalid transitions such as:

```text id="m4s1my"
Succeeded -> Running
Cancelled -> Running
```

unless a future retry mechanism explicitly models this as a new execution attempt.

---

# 4. Task Identity

Every task must have a unique `TaskId`.

Use the domain `TaskId` defined in Task 002.

Do not use array indices or timestamps as the primary identifier.

---

# 5. Task Definition

Define a task definition that describes work before execution.

Conceptually:

```rust
pub struct TaskDefinition {
    pub task_type: TaskType,
    pub service_id: Option<ServiceId>,
    pub workflow_id: Option<WorkflowId>,
    pub dependencies: Vec<TaskId>,
    pub timeout: Option<Duration>,
    pub retry_policy: RetryPolicy,
}
```

Do not copy this structure blindly.

Design the model according to the existing domain contracts.

The important distinction is:

```text
TaskDefinition
    = what should execute

Task
    = runtime state of that execution
```

---

# 6. Task Type

Task type must be extensible.

Initial categories may include:

```text
Git
Build
Install
Liquibase
Process
HealthCheck
CustomWorkflow
```

If a better model exists, use it.

Avoid creating a giant enum that must be modified throughout the application every time a new executor is added.

The system should support future task types without invasive changes.

---

# 7. Task Result

Tasks should have structured results.

Example concepts:

```text
TaskResult
├── success
├── exit_code
├── message
├── output reference
├── error
└── metadata
```

Do not store massive raw stdout directly inside the main task state unless there is a clear reason.

Large output should eventually be handled through the logging system.

---

# 8. Task Progress

Support progress information.

A task may expose:

```text id="v8f4wm"
0%
25%
50%
75%
100%
```

Progress should support:

- Unknown progress
- Percentage progress
- Optional human-readable phase/message

Example:

```text id="1qjuxl"
Progress:
72%

Phase:
Downloading Maven dependencies
```

Do not assume every command provides measurable percentage progress.

Tasks must support indeterminate progress.

---

# 9. Task Messages

Tasks should expose current execution information.

Examples:

```text id="u4hv5s"
"Fetching repository"
"Running Maven build"
"Starting Spring Boot process"
"Waiting for health check"
```

These messages are application data, not TUI-specific rendering.

---

# 10. Task Cancellation

Cancellation is mandatory.

The Task Engine should provide an API similar to:

```rust
cancel(task_id)
```

Cancellation must propagate to the running executor.

A task should not report:

```text
Succeeded
```

after successful cancellation unless the operation actually completed before cancellation.

Cancellation behavior must be deterministic.

---

# 11. Cooperative Cancellation

Prefer cooperative cancellation.

For example:

```text
Task
  ↓
Cancellation Token
  ↓
Executor
```

Use appropriate async cancellation primitives, such as Tokio cancellation mechanisms.

Long-running executors should periodically check for cancellation where technically possible.

---

# 12. Process Cancellation

The Task Engine must support eventual cancellation of external processes.

For example:

```text
Maven Task
    ↓
mvn process
    ↓
Cancellation
    ↓
terminate process
```

The detailed OS process implementation will be provided by the Process Manager later.

For now, define the task/executor contract necessary to support cancellation.

---

# 13. Task Dependencies

Tasks must be able to depend on other tasks.

Example:

```text id="a6eaq8"
Task A
  │
  ├── Task B
  ├── Task C
  │
  └── Task D
        requires B + C
```

Task D cannot execute until B and C satisfy their dependency conditions.

---

# 14. Dependency Policies

The system should support different dependency failure policies.

At minimum consider:

```text id="4y6zps"
Run only if all dependencies succeed
Run if dependencies completed
Do not run if any dependency fails
```

Do not create a complex policy engine unless needed.

Use a simple explicit model that can evolve.

---

# 15. Scheduler

Implement a scheduler responsible for deciding which queued tasks can execute.

The scheduler must consider:

- Task state
- Task dependencies
- Concurrency limit
- Cancellation
- Retry
- Priority if supported
- Timeouts
- Failure propagation

The scheduler should NOT know how Maven, Git, Node, or Liquibase works.

It only knows how to schedule generic tasks.

---

# 16. Concurrency

Support configurable maximum concurrency.

Example configuration:

```toml
[execution]
max_parallel_tasks = 4
```

The scheduler must ensure:

```text
running_tasks <= max_parallel_tasks
```

Independent tasks should run concurrently.

---

# 17. Dependency-Aware Concurrency

Example:

```text id="xjtpqh"
common-core
     │
     ├─────────┐
     ▼         ▼
 auth       payment
     │
     ▼
   users
```

Execution:

```text id="dbm2bj"
common-core
      ↓
auth + payment
      ↓
users
```

`auth` and `payment` may execute concurrently.

`users` must wait until `auth` has satisfied its dependency requirements.

---

# 18. Fairness

Avoid starvation.

If the scheduler supports prioritization, ensure lower-priority tasks can still execute.

Do not implement sophisticated scheduling algorithms unless the current requirements require them.

A predictable FIFO + dependency + concurrency model is acceptable for MVP.

---

# 19. Retry Policy

Support a simple retry model.

Example:

```rust
pub struct RetryPolicy {
    pub max_attempts: u32,
    pub backoff: Duration,
}
```

Retry should be opt-in.

Do not automatically retry every failure.

Destructive operations should generally not be automatically retried.

---

# 20. Task Timeout

Support task-level timeout.

Example:

```text id="c9oh8p"
Build task timeout:
30 minutes
```

A timeout should produce a structured failure such as:

```text
TaskTimeout
```

and trigger cancellation/cleanup where applicable.

---

# 21. Task Registry

The application needs a way to query task state.

Implement a runtime task registry/store.

It should support operations such as:

```text
create
insert
get
list
update
remove/archive
```

For MVP, use an in-memory implementation.

Do NOT introduce a database.

---

# 22. Task History

Completed tasks should remain queryable for a reasonable period.

At minimum, the application should be able to inspect recent:

```text
Succeeded
Failed
Cancelled
Skipped
Blocked
```

tasks.

Task history retention should be configurable in the future.

Do not over-engineer persistence now.

---

The Task Engine should produce task state events.

Potential events:

```text
TaskCreated
TaskStarted
TaskProgressChanged
TaskMessageChanged
TaskSucceeded
TaskFailed
TaskCancelled
TaskSkipped
```

The event mechanism will later be consumed by:

- Ratatui
- MCP

Avoid coupling the event model to UI event types.

---

# 24. Event Delivery

Interfaces should be able to observe task state changes.

Potential model:

```text
TaskEvent
   ↓
Event Stream
   ├──> TUI
   ├──> MCP
   └──> Logging
```

Use idiomatic async mechanisms.

A broadcast/event stream approach may be appropriate.

Do not implement a distributed event broker.

# 25. Task Executor Abstraction

Define a generic task executor boundary.

Conceptually:

```rust
#[async_trait]
pub trait TaskExecutor {
    async fn execute(
        &self,
        task: TaskExecutionContext,
    ) -> Result<TaskResult>;
}
```

The exact API may differ.

The executor must be able to:

- Report progress
- Report messages
- Respect cancellation
- Produce structured results
- Fail with structured errors

---

# 26. Executor Registry

The scheduler should not contain:

```rust
match task.task_type {
    ...
}
```

with huge implementation-specific branches.

Prefer an executor registry or another clean mechanism.

Conceptually:

```text
TaskType
   ↓
Executor Registry
   ↓
Executor
```

For example:

```text
GitFetchTask      -> GitExecutor
MavenBuildTask    -> BuildExecutor
StartProcessTask  -> ProcessExecutor
HealthCheckTask   -> HealthExecutor
```

The registry should support future executors.

---

# 27. Task Execution Context

Define a context that executors can use.

Possible capabilities:

```text
TaskId
Cancellation
Progress reporter
Message reporter
Logger
Execution metadata
```

Do not expose the entire application container to every executor.

Give executors only what they need.

---

# 28. Scheduler/Executor Separation

This distinction is critical:

### Scheduler

Answers:

> When should this task run?

### Executor

Answers:

> How is this task executed?

Example:

```text
Scheduler
    ↓
Start Task
    ↓
Executor
    ↓
Run operation
```

Do not mix the responsibilities.

---

# 29. Workflow Support

The Task Engine should support workflows constructed from tasks.

Example:

```text id="4mgghb"
PrepareEnvironment
      │
      ├── GitSync
      ├── LibraryBuild
      ├── Liquibase
      ├── ServiceBuild
      ├── ServiceStart
      └── HealthCheck
```

The workflow definition should be able to produce a dependency graph of tasks.

Do not implement high-level workflow business logic here.

The application layer creates the workflow.

The Task Engine executes it.

---

# 30. Task Graph Validation

Before executing a workflow, validate:

- Unknown task dependencies
- Duplicate task IDs
- Cycles
- Invalid dependency states

At minimum detect cycles.

Example invalid graph:

```text
A -> B
B -> C
C -> A
```

Return a structured error.

---

# 31. Deadlock Prevention

The scheduler must not deadlock silently.

Example:

```text
A waits for B
B waits for A
```

This should be detected as an invalid dependency graph before scheduling.

---

# 32. Task Cancellation Semantics

Define behavior when a parent workflow is cancelled.

Example:

```text
Workflow
 ├── Task A
 ├── Task B
 └── Task C
```

If the workflow is cancelled:

- Running tasks should receive cancellation.
- Queued tasks should become cancelled or skipped according to policy.
- Dependent tasks should not start.
- Final workflow state should be deterministic.

Document the chosen semantics.

---

# 33. Failure Propagation

Define what happens when a task fails.

Example:

```text
A succeeds
B fails
C depends on B
```

Expected:

```text
A -> Succeeded
B -> Failed
C -> Blocked/Skipped
```

Do not start dependent tasks after a required dependency failure.

---

# 34. Task Idempotency

The Task Engine itself should not assume all operations are idempotent.

Executors/application use cases are responsible for determining operation semantics.

However, the Task Engine must provide enough metadata to distinguish:

- New task
- Retry
- Re-run
- Cancellation
- Duplicate request

---

# 35. Duplicate Execution Protection

Avoid accidentally starting the same service twice from concurrent requests.

For example:

```text
TUI: Start auth-service
MCP: Start auth-service
```

at nearly the same time should not blindly spawn two processes.

Design a service-level locking/operation coordination boundary.

You do not need to implement full service locking in this task if the application layer will own it, but establish the correct place for this responsibility.

Document the decision.

---

# 36. Backpressure

The task system should not create unbounded work.

If hundreds of operations are requested:

```text
Task Queue
```

should remain bounded or otherwise controlled.

Do not allow an AI agent or future client to accidentally enqueue unlimited tasks.

A reasonable MVP policy may be:

```text
max_queued_tasks
```

configuration.

If you implement this, document the behavior.

---

# 37. Task Query API

Provide application-friendly operations such as:

```text
get_task(task_id)
list_tasks()
list_running_tasks()
list_recent_tasks()
```

Avoid interface-specific result types.

---

# 38. Task Event Subscription

Provide a mechanism for consumers to subscribe to task events.

Future consumers:

```text
Ratatui
MCP
CLI
Logging
Metrics
```

The event API must remain interface-neutral.

---

# 39. Thread Safety

The Task Engine will be accessed concurrently by:

- TUI event loop
- MCP request handlers
- Background scheduler
- Executors
- Event subscribers

Design shared state carefully.

Avoid excessive locking.

Prefer appropriate Tokio synchronization primitives where async state is required.

Document important concurrency decisions.

---

# 40. Shutdown

The Task Engine must support graceful shutdown.

On application shutdown:

1. Stop accepting new tasks.
2. Notify running tasks.
3. Allow cancellation/cleanup.
4. Stop scheduler workers.
5. Publish final task states where appropriate.
6. Exit cleanly.

Do not leave background scheduler tasks running.

# 49. Long-Running Operations

Do not block application APIs unnecessarily.

Prefer:

```text
Operation request
      ↓
TaskId
```

rather than waiting for a potentially long operation.

The caller can then query:

```text
get_task(task_id)
```

or subscribe to task events.

This model is especially important for MCP.

---

# 50. MCP Readiness

Although MCP is not implemented yet, ensure the Task Engine can support MCP use cases.

For example:

```text

     ↓
TaskId
     ↓

     ↓

```

AI agents should not need to maintain an opaque long-running request.

# 51. TUI Readiness

Although TUI is not implemented yet, ensure the TUI can:

- List tasks
- Show progress
- Show task messages
- Show task failures

# 52. Performance

The Task Engine should be capable of handling at least:

```text
40 repositories
100+ repositories
```

with a reasonable number of concurrent tasks.

Do not spawn one Tokio worker per repository by default.

Use bounded concurrency.

Avoid unnecessary task polling loops.

Prefer event-driven notifications where practical.

- Task type
- Workflow ID where available
- Start/end time
- Outcome
- Error details

Do not log sensitive environment variables.
