# 2. Goal

Implement a production-quality **Health Manager and Observability layer** for locally managed services.

The system must support:

- Process health checks
- TCP port checks
- HTTP health checks
- Spring Boot Actuator health checks
- Configurable readiness checks
- Health status tracking
- Health-check timeouts
- Retry and polling policies
- Realtime log streaming
- Historical log retrieval
- Log filtering
- Task and service event correlation
- Structured diagnostics

The implementation must remain independent from Ratatui and MCP.

Both interfaces must eventually consume the same application-level capabilities.

---

# 3. Architectural Principles

Separate these responsibilities.

## Health Manager

Determines whether a service is:

- Running
- Reachable
- Ready
- Healthy
- Unhealthy
- Unknown

## Process Manager

Owns:

- Process lifecycle
- PID tracking
- stdout/stderr capture
- Process exit detection

## Observability Layer

Owns:

- Log retrieval
- Log persistence
- Log filtering
- Event correlation
- Diagnostic summaries

## Task Engine

Owns:

- Scheduling
- Task lifecycle
- Cancellation
- Timeouts
- Task events

Do not duplicate these responsibilities.

This is illustrative.

Adapt it to existing domain and application contracts.

Do not introduce a large plugin framework.

# 7. Process Health Check

Use the existing Process Manager.

Do not independently scan the operating system for arbitrary processes.

A process health check should determine whether the Service Orchestrator-managed process is alive.

Possible result:

```json
{
  "service": "auth-service",
  "checkType": "process",
  "status": "healthy",
  "details": {
    "managedProcess": true,
    "running": true
  }
}
```

Do not treat an unrelated process using the same port as a managed service.

---

# 8. TCP Health Check

Support TCP connection checks.

Example:

```text
localhost:8081
```

The checker should attempt a TCP connection with a configurable timeout.

A successful TCP connection indicates reachability, not application-level readiness.

Do not report a service as fully healthy based only on TCP reachability when stronger checks are configured.

---

# 9. HTTP Health Check

Support configurable HTTP endpoints.

Example:

```text
http://localhost:8081/actuator/health
```

Configuration should support:

- URL
- Method, initially GET
- Timeout
- Expected status codes
- Optional response validation
- Retry policy

Avoid exposing sensitive headers in logs.

Do not follow redirects to arbitrary destinations without an explicit policy.

---

# 10. Spring Boot Actuator

Support Spring Boot 3 Actuator health endpoints.

Examples:

```text
/actuator/health
/actuator/health/readiness
```

Do not assume Actuator is enabled in every service.

Do not hard-code a universal port or path.

Where configured, interpret Spring Boot health status values such as:

```text
UP
DOWN
OUT_OF_SERVICE
UNKNOWN
```

Do not assume HTTP 200 always means the application reports `UP`.

Handle malformed or unavailable responses gracefully.

---

# 11. Health State Model

Reuse or extend existing domain health states.

Consider:

```text
Unknown
Checking
Healthy
Unhealthy
Degraded
Unreachable
```

Keep health state separate from process state.

For example:

```text
Process: Running
Health: Unhealthy
```

is a valid combination.

Likewise:

```text
Process: Running
Health: Checking
```

is valid during startup.

---

# 12. Readiness vs Liveness

Distinguish:

- Process liveness
- Network reachability
- Application readiness

A service may have started its process but still be initializing.

Do not mark it ready prematurely.

For example:

```text
Starting
   |
   v
Process Running
   |
   v
Port Open
   |
   v
HTTP Readiness UP
   |
   v
Ready
```

Not every service requires all stages.

Use validated service configuration to determine the required checks.

# 14. Health Check Aggregation

A service may have multiple health checks.

Example:

```text
auth-service
    |
    +---- Process Check
    +---- TCP Check
    +---- HTTP Check
```

Define deterministic aggregation rules.

For example:

- All required checks healthy → Healthy
- Required check failed → Unhealthy
- Required check pending → Checking
- Optional check failed → Degraded, if supported

Document the exact semantics.

Do not average health statuses into arbitrary percentages.

---

# 15. Health Polling

Support periodic health checks where configured.

Requirements:

- Configurable interval
- Configurable timeout
- Cancellation
- Shutdown
- No duplicate polling loops
- Bounded concurrency
- No unnecessary busy polling

Do not poll every configured service continuously by default.

Prefer monitoring actively managed services or explicitly selected services.

---

# 16. Startup Readiness

Integrate health checks with Service Runtime where appropriate.

The application should eventually support:

```text
Start Service
      |
      v
Process Started
      |
      v
Wait for Readiness
      |
      v
Ready
```

Do not change the existing startup task lifecycle without reviewing Task 010 semantics.

A startup task may complete after successful process spawning, while a separate readiness operation continues.

If readiness waiting is introduced, represent it explicitly.

Do not leave long-running startup tasks permanently active.

# 24. Log Filtering

Support filtering by:

- Service
- Task
- Process
- Severity
- Source
- Time range
- Text search, where practical

---

# 25. Log Pagination

MCP clients must not receive unbounded logs.

Design the log query API to support:

- Limit
- Cursor or offset
- Time range
- Truncation indicator

Prefer cursor-based pagination if it fits the existing storage model.

Do not create unstable pagination behavior when logs are appended concurrently.

---

# 26. Log Retention

Use bounded in-memory buffering.

Support configurable file retention where existing logging infrastructure permits.

Do not allow a continuously running service to consume unlimited memory through log accumulation.

Document retention defaults.

---

# 27. Log Backpressure

Slow consumers must not block managed service processes.

If a subscriber cannot keep up:

- Use bounded channels
- Drop or truncate according to an explicit policy
- Expose dropped-message counts where practical

Do not silently block stdout/stderr readers indefinitely.

---

# 28. Secret Redaction

Logs may contain sensitive information.

Do not expose:

- Database passwords
- Access tokens
- Private keys
- Credential-bearing URLs
- Secret environment values

Reuse existing redaction mechanisms.

Do not claim perfect secret detection.

Avoid logging sensitive inputs in the first place.

---
