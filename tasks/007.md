# 2. Goal

Implement a production-quality, reusable **Git Manager** that manages Git repositories through the existing Process Manager.

The Git Manager must support individual repositories and bulk operations across multiple repositories.

The primary use case is managing approximately 40 frontend, backend, and library repositories in a single development workspace.

The implementation must remain scalable to 100+ repositories.

Git Manager must be independent of Ratatui and MCP.

Both interfaces will eventually consume the same application-level Git capabilities.

## Core architecture

```text
              Ratatui TUI
                   |
                   |
              MCP Server
                   |
                   v
           Application Core
                   |
                   v
             Git Manager
                   |
                   v
              Task Engine
                   |
                   v
             Process Manager
                   |
                   v
               Git CLI
                   |
                   v
           Local Repositories
```

This diagram is conceptual.

The actual execution flow must respect the existing application and task architecture.

Do not create circular dependencies between Git Manager, Task Engine, and Process Manager.

# 3. Architectural Constraints

The following rules are mandatory.

1. Git Manager must not directly spawn OS processes.
2. All Git CLI execution must go through the Process Manager.
3. Long-running Git operations must integrate with the Task Engine.
4. Git Manager must not depend on Ratatui.
5. Git Manager must not depend on MCP.
6. Git Manager must not parse TOML configuration directly.
7. Repository definitions must come from validated application configuration.
8. Git operations must return structured results.
9. Destructive operations must respect application security policies.
10. Git operations must never silently discard local developer changes.

Prefer using the installed Git CLI rather than introducing `git2`, unless the existing architecture provides a compelling reason otherwise.

# 4. Git Operations

Implement the following operations.

## 4.1 Repository Status

Provide structured repository status information.

Include:

- Repository existence
- Repository validity
- Current branch
- Detached HEAD state
- Current commit SHA
- Upstream branch
- Working tree status
- Staged changes
- Unstaged changes
- Untracked files
- Merge conflicts
- Ahead/behind counts where available
- Remote information

Use Git's machine-readable output formats where possible.

Prefer porcelain formats for status parsing.

Do not parse human-readable, localized Git output when a stable machine-readable alternative exists.

## 4.2 Fetch

Support:

- Fetch configured remote
- Fetch selected repository
- Fetch multiple repositories
- Optional prune behavior
- Cancellation
- Timeout
- Progress reporting

Fetching must not modify local working-tree files.

## 4.3 Pull

Support safe repository updates.

Prefer fast-forward-only behavior by default.

Do not silently create merge commits or rebase local commits.

Before pulling:

1. Validate repository.
2. Validate branch.
3. Inspect working-tree state.
4. Verify upstream configuration.
5. Check whether the operation is safe.
6. Execute pull only when preconditions are satisfied.

Diverged branches must produce actionable errors.

## 4.4 Checkout

Support checking out an existing local or remote-tracking branch.

Requirements:

- Configurable target branch
- Branch existence validation
- Detached HEAD handling
- Working-tree safety checks
- Clear error reporting
- Tracking branch setup when appropriate

Never silently discard uncommitted changes.

Do not hard-code `master`.

## 4.5 Branch Listing

Support listing:

- Local branches
- Remote branches
- Current branch
- Tracking relationships

Return structured branch information.

## 4.6 Clone

Support cloning repositories that are not yet available locally.

Requirements:

- Configured repository URL
- Configured local path
- Optional target branch
- Clone progress
- Cancellation
- Timeout
- Destination validation

Never overwrite an existing non-empty directory without explicit authorization.

## 4.7 Repository Diff

Support read-only diff inspection.

At minimum:

- Unstaged diff
- Staged diff
- File-level change summary

Avoid returning unbounded diff output.

Provide output-size limits.

## 4.8 Destructive Operations

Design and implement guarded support for:

- Hard reset
- Git clean
- Discarding local changes

These operations must require explicit authorization through the application policy layer.

Do not implement unrestricted destructive Git commands.

If the existing policy system cannot securely authorize them, implement validation and planning only, and report the limitation.

# 8. Multi-Repository Operations

Support operations across selected repositories.

Examples:

```text
Sync selected backend services
Fetch all frontend repositories
Checkout master for selected services
Inspect status of all libraries
```

Bulk operations must use the existing Task Engine and Scheduler.

Do not create a second concurrency framework inside Git Manager.

Use the configured concurrency limits.

For example:

```toml
[execution]
max_parallel_tasks = 4
```

Each repository operation must have an independent result.

Failure in one repository must not automatically destroy or invalidate successful operations in unrelated repositories.

Provide a bulk operation summary.

Example:

```json
{
  "total": 4,
  "succeeded": 3,
  "failed": 1,
  "cancelled": 0
}
```

Support cancellation of bulk operations through the Task Engine.

# 12. Operation Coordination

Prevent conflicting Git mutations on the same repository.

Example:

```text
Task A: checkout auth-service
Task B: pull auth-service
```

These operations must not run concurrently against the same repository.

Implement or reuse a repository-scoped operation coordination mechanism.

Independent repositories should still be processed concurrently.

Read-only operations may run concurrently when safe.

Do not introduce unnecessary global locking.

# 13. Cancellation

Git operations must respect Task Engine cancellation.

Cancellation should propagate to the Process Manager.

When cancellation occurs:

- Stop the relevant Git process.
- Preserve accurate task state.
- Capture available error/output information.
- Reinspect repository state if necessary.
- Do not claim a rollback occurred unless it actually did.

Git operations are not generally transactional.

Document partial completion behavior.
