# Task 028 — Architecture Simplification & Technical Debt Reduction

## Role

Act as a Principal Rust Engineer, Software Architect, Refactoring Specialist, and React/TypeScript Architect.

You are implementing **Task 028 — Architecture Simplification & Technical Debt Reduction** of the Service Orchestrator project.

Your objective is to reduce unnecessary architectural complexity, eliminate confirmed technical debt, and improve maintainability without changing the application's externally observable behavior.

This is a single, end-to-end engineering task.

Do not stop after planning. Audit, identify justified simplifications, implement safe refactoring, test, document, and report the completed work.

---

# 1. Execution Strategy

Follow these rules:

- Read `AGENTS.md` completely.
- Read documentation directly relevant to the affected modules.
- Inspect the actual codebase before making decisions.
- Do not assume an abstraction is unnecessary merely because it has one implementation.
- Prefer measurable simplification over stylistic refactoring.
- Preserve public APIs where practical.
- Preserve runtime behavior.
- Preserve existing security boundaries.
- Run focused tests during implementation.
- Run full validation at completion.
- Avoid unrelated feature development.
- Maintain a concise progress record in `docs/task-028-progress.md` if useful for context recovery.

**Do not stop after producing an architecture review. Implement justified simplifications and verify them.**

# 2. Project Context

Service Orchestrator is a local macOS developer orchestration application.

It supports:

- Git repository management
- Maven/npm builds
- Shared library management
- Liquibase migrations
- Local service lifecycle management
- Health checks
- Logs
- Development workflows
- Multiple workspaces
- Ratatui TUI
- MCP Server
- Tauri 2 + React + TypeScript GUI

All interfaces communicate with a shared local Rust daemon.

The application is intended for local development only.

It does not require a remote backend, Kubernetes deployment, or an LLM.

# 5. Architecture Audit

Inspect the existing dependency graph.

Identify:

- Circular dependencies
- Unnecessary dependency chains
- Duplicate domain models
- Duplicate DTOs
- Duplicate service layers
- Excessive trait indirection
- Redundant adapters
- Unused registries
- Unused configuration fields
- Unreachable code
- Obsolete compatibility layers

Document confirmed findings.

Do not refactor based only on subjective preferences.

---

# 6. Preserve Essential Architecture

The following boundaries are intentional and should normally remain:

```text
GUI / TUI / MCP
       |
       v
Local IPC
       |
       v
Shared Daemon
       |
       v
Application Core
       |
       v
Infrastructure
```

The shared daemon is necessary for cross-interface runtime state consistency.

Do not eliminate IPC merely to reduce the number of layers.

Do not create separate application engines for each interface.

---

# 7. Rust Crate Boundaries

Review the Cargo workspace.

Evaluate whether each crate represents a meaningful architectural boundary.

Potential simplifications:

- Merge tiny crates that exist only for speculative modularity.
- Consolidate closely related utility modules.
- Remove redundant wrapper crates.
- Reduce unnecessary cross-crate dependencies.

However:

- Do not merge crates solely to reduce crate count.
- Preserve meaningful domain/application/infrastructure boundaries.
- Avoid broad crate restructuring without clear benefits.

---

# 8. Trait and Interface Audit

Review existing Rust traits.

For each trait, determine:

- How many implementations exist?
- Does it represent an actual architectural boundary?
- Is it needed for testing?
- Is it needed for runtime polymorphism?
- Is it needed for provider extensibility?
- Does it introduce unnecessary indirection?

Do not remove traits that provide real value.

---

# 9. Provider Registry Review

Inspect:

- BuildProvider
- MigrationProvider
- ServiceRuntime
- HealthChecker
- Other provider abstractions

Evaluate whether each registry is justified.

Keep provider abstractions where different implementations already exist or where extension is a concrete requirement.

For example:

- Maven and npm BuildProviders are real implementations.
- Java and Node runtimes are real implementations.

A single-provider registry may be simplified if it adds complexity without providing useful separation.

Do not implement Gradle, Flyway, Docker, or Kubernetes.

---

# 10. Application Core Simplification

Inspect application use cases.

Look for:

- Duplicate validation
- Redundant request mapping
- Excessive service wrappers
- Repeated error conversion
- Duplicate workflow construction
- Unnecessary forwarding methods

Consolidate repeated behavior where appropriate.

Do not move business logic into GUI, TUI, MCP, or IPC handlers.

---

# 11. Task Engine Review

Inspect Task Engine abstractions.

Evaluate:

- TaskDefinition complexity
- Executor registry
- Task state storage
- Event handling
- Retry policies
- Cancellation
- Scheduling interfaces

Do not rewrite the scheduler.

Remove only confirmed redundant complexity.

Preserve concurrency, cancellation, dependency ordering, and task identity.

---

# 12. Workflow Engine Review

Inspect workflow planning and execution.

Look for:

- Duplicate dependency graph logic
- Redundant workflow models
- Repeated task construction
- Excessive state conversion
- Unnecessary orchestration layers

Prefer one authoritative workflow representation.

Do not duplicate workflow logic in frontend adapters.

---

# 13. IPC Contract Simplification

Inspect the IPC protocol and DTOs.

Look for:

- Duplicate request models
- Duplicate response models
- Repeated serialization logic
- Redundant error wrappers
- Unnecessary protocol translation layers

Simplify while preserving protocol compatibility.

Do not remove protocol versioning, authorization, or request validation.

---

# 14. Tauri Adapter Simplification

Inspect Tauri commands.

Look for:

- Repeated request validation
- Duplicate error mapping
- Redundant IPC client wrappers
- Repeated event forwarding logic

Create shared helpers only where duplication is real.

Do not introduce a generic framework for every Tauri command.

---

# 15. React Architecture Audit

# 16. React State Simplification

The daemon is the authoritative source of application state.

Avoid maintaining multiple independent copies of:

- Services
- Tasks
- Workflows
- Health
- Logs

Prefer a consistent server-state strategy.

Keep UI-specific state local where appropriate.

Do not introduce Redux or another large state framework without justification.

---

# 17. Shared Components

Consolidate genuinely duplicated UI components.

Examples:

- Status indicators
- Error panels
- Confirmation dialogs
- Task progress
- Operation results
- Loading states
- Empty states

Do not create excessively generic components that are harder to understand than the originals.

---

# 18. Domain Model Review

Inspect domain types.

Identify:

- Duplicate identifiers
- Redundant enums
- Overlapping state models
- Unused metadata
- Unnecessary wrappers
- Invalid state combinations

Preserve strong types where they prevent real mistakes.

Do not replace meaningful domain types with arbitrary strings solely to reduce code.

# 19. Error Handling Simplification

Look for:

- Duplicate error variants
- Unnecessary wrapping
- Lost error context
- Repeated mapping logic

Do not expose sensitive internal details.

# 20. Configuration Simplification

Review configuration models.

Identify:

- Unused fields
- Duplicate settings

- Obsolete compatibility handling
- Unnecessary configuration layers

# 21. Remove Dead Code

Identify unused:

- Functions
- Traits
- Modules
- Components
- Hooks
- Types
- Dependencies
- Feature flags

Remove confirmed dead code.

Do not delete code merely because static analysis cannot find dynamic or externally invoked references.

---

# 22. Dependency Cleanup

Review Cargo and npm dependencies.

Remove dependencies that are genuinely unused.

Avoid unnecessary upgrades.

Do not introduce new libraries to replace a few lines of straightforward code.

Preserve lockfile consistency.

---

# 23. Avoid Premature Generalization

Look for abstractions designed exclusively for hypothetical future features.

Examples:

- Dynamic provider loading without a real requirement
- General-purpose plugin frameworks
- Complex event brokers
- Multi-user authorization frameworks
- Distributed workflow abstractions
- Remote execution layers

Simplify only when safe.

Do not remove planned extension points that are inexpensive and already useful.

---

- IPC authorization
- MCP tool validation
- Git safety
- Migration target restrictions
- Process ownership
- Secret redaction
- Resource limits
- Tauri permissions

# 26. Refactoring Prioritization

1. Confirmed maintenance burden
2. Duplicate logic
3. Complexity reduction
4. Testability improvement
5. Risk of regression

6. Verify behavior remains equivalent.

Do not combine many unrelated changes without intermediate validation.
