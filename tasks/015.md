# 3. Architectural Problem

Currently, independent processes may initialize independent application cores.

Example:

```text
TUI Process
    |
    +-- Task Engine A
    +-- Process Registry A

MCP Process
    |
    +-- Task Engine B
    +-- Process Registry B
```

This can cause:

- Inconsistent service status
- Duplicate process startup
- Inconsistent task history
- Inability to stop processes started by another interface
- Conflicting Git/build operations
- Conflicting migrations
- Inconsistent logs and health status

The new architecture must address these problems.

---

# 4. Target Architecture

Use a shared local orchestration engine.

```text
                   Human Developer
                          |
                          v
                     Ratatui TUI
                          |
                          v
                    Local IPC
                          |
                          |
AI Agent --> MCP Server --+
                          |
                          v
                Service Orchestrator
                    Local Daemon
                          |
                  Application Core
                          |
              +-----------+-----------+
              |           |           |
              v           v           v
          Task Engine   Runtime    Policy Engine
              |         Manager
              |           |
              +-----+-----+
                    |
              Infrastructure
                    |
        +-----------+-----------+
        |           |           |
       Git         Build      Processes
```

The daemon must be the authoritative owner of mutable runtime state.

TUI and MCP must act as clients.

---

# 5. Single Binary Requirement

Preserve the single-binary architecture.

The binary should support:

```bash
service-orchestrator daemon
service-orchestrator tui
service-orchestrator mcp
```

Do not create separate executable artifacts for the daemon and clients.

Do not introduce a mandatory external backend.

The daemon is a local process running the same Rust binary.

---

# 6. Daemon Lifecycle

Design a reliable daemon lifecycle.

The daemon should:

1. Load validated configuration.
2. Initialize Application Core.
3. Initialize Task Engine.
4. Initialize Process Manager.
5. Initialize Service Runtime.
6. Initialize policy and observability systems.
7. Bind a local IPC endpoint.
8. Accept client connections.
9. Execute application requests.
10. Publish state changes.
11. Shut down gracefully.

The daemon must not initialize Ratatui or MCP transport internally unless explicitly required by the architecture.

---

# 7. Local IPC

Prefer Unix Domain Sockets for macOS.

Example:

```text
~/.service-orchestrator/run/daemon.sock
```

The socket path must be configurable.

Use a versioned, structured IPC protocol.

Do not use arbitrary shell commands as IPC requests.

Do not expose the daemon through a public TCP port for MVP.

---

# 8. IPC Protocol

Define structured request and response messages.

Conceptually:

```json
{
  "requestId": "abc123",
  "version": 1,
  "operation": "start_service",
  "payload": {
    "workspaceId": "project-x",
    "serviceId": "auth-service"
  }
}
```

Response:

```json
{
  "requestId": "abc123",
  "success": true,
  "data": {
    "taskId": "task-123"
  }
}
```

This is illustrative.

Choose an appropriate serialization format and framing strategy.

Consider JSON with length-prefixed framing for simplicity.

Do not build a complex RPC framework unnecessarily.

---

# 9. IPC Architecture

Separate:

- Transport
- Serialization
- Request routing
- Application dispatch
- Error mapping

The IPC layer must not implement business logic.

Correct:

```text
IPC Request
    |
    v
Request Dispatcher
    |
    v
Application Core
    |
    v
Task Engine
```

Incorrect:

```text
IPC Handler
    |
    v
Direct Git / Maven / Process execution
```

# 10. Shared Application State

The daemon must own:

- Active tasks
- Task history
- Process registry
- Service runtime state
- Health state
- Operation coordination
- Active workflow state
- Log subscriptions

Clients must not maintain competing authoritative copies.

Client-side UI caches are allowed but must be refreshable.

# 11. Client Abstraction

```rust
pub trait OrchestratorClient {

        &self,

```

Adapt to existing APIs.

Avoid creating one enormous trait with every possible operation if smaller interfaces are cleaner.

# 14. Automatic Daemon Startup

The user should not be forced to manually start the daemon before opening the TUI.

Desired experience:

```bash
service-orchestrator tui
```

If the daemon is already running:

- Connect to it.

If the daemon is not running:

- Start it safely.
- Wait for readiness.
- Connect.

The same behavior should apply to MCP mode where appropriate.

---

# 15. Startup Race Conditions

Two clients may launch simultaneously.

Example:

```text
TUI starts
MCP starts
```

Both may attempt to start the daemon.

Ensure only one authoritative daemon starts.

Use a reliable single-instance mechanism.

Do not rely solely on checking whether a socket file exists.

Handle stale socket files safely.

---

# 16. macOS Process Lifecycle

Design daemon process management for macOS.

Consider:

- Process detachment
- Session management
- Signal handling
- Parent process exit
- Child process ownership
- Graceful shutdown
- Unexpected daemon termination

Do not assume Linux-specific process behavior applies unchanged.

# 17. Service Process Ownership

The daemon must own managed service processes.

A service started from TUI must remain manageable from MCP.

A service started from MCP must remain manageable from TUI.

Example:

```text
TUI -> Start auth-service
          |
          v
        Daemon
          |
          v
    auth-service RUNNING

MCP -> Get auth-service status
          |
          v
        RUNNING
```

Prevent duplicate service startup across clients.

---

# 18. Daemon Restart Behavior

Define behavior after daemon restart.

The system must not blindly assume all previously managed processes are still running.

At minimum:

- Detect stale runtime state.
- Avoid PID reuse mistakes.
- Avoid killing unrelated processes.
- Report uncertain ownership accurately.

Do not implement unsafe process adoption based only on PID or port.

Document limitations if full process recovery is deferred.

---

# 19. Task State Sharing

Tasks submitted through any client must be visible to all clients.

Example:

```text
MCP -> Build auth-service
          |
          v
       Task #123

TUI -> Tasks
          |
          v
       Task #123 RUNNING
```

The daemon must own the Task Engine.

Clients must not create independent task registries.

---

# 20. Event Streaming

Support realtime state updates over IPC.

Potential events:

- Task state changed
- Task progress changed
- Service started
- Service stopped
- Health changed
- New log entry

Use bounded subscriptions.

Avoid blocking the daemon when a client is slow.

---

# 21. Reconnection

Clients must handle daemon disconnection.

The TUI should:

- Display connection status.
- Attempt safe reconnection.
- Refresh state after reconnecting.
- Avoid duplicating operations.

MCP should return structured errors when the daemon is unavailable.

Do not silently retry mutating operations when their execution status is uncertain.

---

# 22. Request Identity

Use unique request identifiers.

Support correlation between:

- Client request
- IPC request
- Application operation
- Task ID

Avoid duplicate execution caused by automatic retries.

Design an idempotency strategy for mutating operations where necessary.

---

# 23. Authorization

The daemon must enforce application policies.

Do not trust clients merely because they connect through a local socket.

Protected operations must not bypass authorization.

TUI confirmation and MCP authorization must use the same trusted policy model.

Do not treat a client-provided boolean such as `confirmed: true` as sufficient authorization.

---

# 24. IPC Security

The IPC endpoint must be local and protected.

Requirements:

- Restrict socket permissions.
- Validate peer identity where supported.
- Reject malformed messages.
- Limit request sizes.
- Prevent unauthorized filesystem access.
- Avoid exposing secrets.
- Avoid arbitrary command execution.

Prefer a private per-user runtime directory with restrictive permissions.

---

# 25. Protocol Versioning

Version the IPC protocol.

Example:

```text
protocol_version = 1
```

Clients and daemon must negotiate or validate compatibility.

Return actionable errors for incompatible versions.

Do not silently interpret incompatible messages.

---

# 26. Configuration Consistency

The daemon should own the active validated configuration snapshot.

TUI and MCP must not independently mutate configuration files while the daemon is running.

Configuration editing is deferred to a later task.

For this task, support consistent configuration loading and read-only inspection.

# 27. Logging

- Client type

- Task ID
- Outcome
- Duration

MCP stdout must remain reserved for protocol messages.

Daemon logs should go to stderr or configured files as appropriate.

# 28. Graceful Shutdown

Support an explicit daemon shutdown operation.

Shutdown must:

1. Stop accepting new requests.
2. Notify connected clients.
3. Stop accepting new tasks.
4. Apply the existing managed-process shutdown policy.
5. Cancel or finish active operations according to policy.
6. Release IPC resources.
7. Exit cleanly.

Do not unexpectedly terminate developer services merely because the TUI window closes.

Daemon shutdown and TUI exit are different operations.

---

# 29. Client Exit Semantics

Closing the TUI must not automatically stop the daemon.

Closing an MCP client must not automatically stop the daemon.

The daemon should continue managing running services.

Provide an explicit shutdown command for the daemon.
