# Task 021 — Migration, Tasks, Health & Realtime Logs GUI

## Role

Act as a Principal Rust Engineer, Senior Tauri 2 Engineer, React/TypeScript Architect, and macOS Desktop Application Engineer.

You are implementing **Task 021 — Migration, Tasks, Health & Realtime Logs GUI** of the Service Orchestrator project.

Your responsibility is to deliver a complete, functional implementation of four desktop management areas:

1. Migration Management
2. Task Management
3. Health Monitoring
4. Realtime and Historical Logs

This is a single, end-to-end implementation task.

Do not stop after planning or initial scaffolding. Implement, test, fix, document, and report the completed work.

# PART A — MIGRATION MANAGEMENT

## 4. Migration Screen

Implement a fully functional Migration Management screen.

Display:

- Service name
- Workspace
- Migration provider
- Migration enabled/disabled
- Database target identity
- Environment
- Latest migration status
- Pending changesets, when available
- Last execution result
- Last execution timestamp

Use real Application Core data.

Do not fabricate migration information.

## 5. Migration Operations

Support existing operations:

- Validate configuration
- Inspect migration status
- Inspect pending changes
- Generate SQL preview
- Apply migration
- View migration logs

Only expose operations actually supported by the backend.

Render unsupported capabilities as unavailable rather than pretending they work.

## 6. Migration Details

Create a detail panel showing:

- Service information
- Migration provider
- Target database identity
- Environment
- Configured capabilities
- Latest task
- Latest error
- Pending changesets, if known

Never expose credentials or secret connection information.

## 7. SQL Preview

Implement a read-only SQL preview interface.

Support:

- Monospaced SQL rendering
- Search
- Copy
- Line wrapping
- Bounded output
- Truncation indicators

SQL preview must not execute statements.

Clearly communicate that preview results may become stale if database state changes.

## 8. Migration Execution

Implement Apply Migration through the existing Application Core.

Expected flow:

```text
Select Service
      |
      v
Inspect Target
      |
      v
Review Operation
      |
      v
Authorization
      |
      v
Submit Task
      |
      v
Monitor Execution
      |
      v
Display Result
```

All authorization must be enforced by the daemon.

A frontend confirmation boolean must not be treated as trusted authorization.

If secure authorization is unavailable, block the protected operation and display an actionable explanation.

## 9. Migration Safety

Migration execution can modify database schemas.

Requirements:

- Display the target environment.
- Display a safe database identifier.
- Distinguish local and non-local targets.
- Enforce existing policy decisions.
- Never automatically execute against shared, staging, or production databases.
- Never automatically retry failed migrations.
- Never automatically release Liquibase locks.
- Never claim cancellation rolled back database changes.

Support bulk migration only through an existing coordinated backend workflow.

Do not create independent frontend migration loops that bypass database locking.

# PART C — HEALTH MONITORING

## 17. Health Dashboard

Implement a functional Health Monitoring screen.

Display:

- Service
- Runtime state
- Overall health

- TCP health
- HTTP health

## 18. Health State Semantics

Keep runtime state separate from health state.

For example:

```text
Runtime: RUNNING
Health: UNHEALTHY
```

is valid.

Do not assume a running process is healthy.

Distinguish readiness, reachability, and process liveness where supported.

## 19. Health Details

Create a detailed health view showing:

- Configured checks
- Check types
- Required/optional checks
- Last result
- Duration
- Failure reason
- Last checked timestamp

Support existing:

- Process checks
- TCP checks
- HTTP checks
- Spring Boot Actuator checks through HTTP

## 20. Manual Health Checks

Allow users to trigger health checks through Application Core.

Do not perform direct HTTP requests from React.

Do not create a second frontend health-check scheduler.

## 21. Realtime Health Events

Subscribe to existing daemon health events.

Update the UI when:

- Health checks complete
- Services become healthy
- Services become unhealthy
- Readiness changes

Avoid duplicate subscriptions and unnecessary full-workspace refreshes.

## 22. Health History

Display recent health history where supported.

Possible information:

- Last healthy timestamp

If history is unavailable, display an explicit unavailable state.

- Confirmation dialogs

## 32. Typed Desktop API

Extend the existing typed desktop API.

Use strongly typed request and response models.

## 33. Tauri Adapter

Keep Tauri handlers thin.

- Validate input

- Map results

- Execute Liquibase directly
- Perform health probes directly
- Manage task scheduling

- Bypass authorization

## 34. Event Subscriptions

Reuse existing daemon event infrastructure.

Ensure:

- Correct subscription lifecycle
- Cleanup on unmount
- Reconnection support
- No duplicate listeners
- Workspace scoping
- Protection against stale updates

## 35. Workspace Switching

When the active workspace changes:

- Update migration data.
- Update task filters.
- Update health information.
- Update log subscriptions.
- Cancel obsolete reads where appropriate.
- Prevent stale responses from overwriting new workspace data.

Do not mix data from different workspaces.

## 36. Daemon Disconnection

When the daemon disconnects:

- Display connection status.
- Disable mutating actions.
- Preserve safe UI state.
- Attempt safe reconnection.
- Refresh authoritative state.
- Reestablish subscriptions.

Do not automatically replay mutating operations whose outcome is uncertain.
