# Goal

Implement the initial configuration system for Service Orchestrator.

The system must be configuration-driven.

Service definitions, workspace definitions, profiles, groups, commands, runtimes, dependencies, libraries, health checks, and execution settings must NOT be hard-coded into application logic.

Configuration should be loaded from a versioned TOML file and converted into validated application/domain configuration.

---

# 1. Design Requirements

The configuration system must provide:

```text
Config File
    ↓
Parse
    ↓
Deserialize
    ↓
Validate
    ↓
Normalize / Resolve
    ↓
Application Configuration
    ↓
Application Core
```

Separate:

1. Raw configuration representation
2. Validation
3. Domain/application representation

Do not let TOML-specific implementation details leak throughout the application.

---

# 2. Configuration Location

Define a sensible default configuration directory for macOS.

Preferred:

```text
~/.service-orchestrator/
```

Suggested structure:

```text
~/.service-orchestrator/
├── config.toml
├── workspaces/
├── profiles/
└── logs/
```

The exact filesystem layout may be improved if there is a strong reason.

Make paths configurable where appropriate.

---

# 3. Configuration Version

The configuration format must be versioned.

Example:

```toml
config_version = 1
```

Reject unsupported configuration versions with a clear error.

Do not silently interpret an unknown schema version.

Design the loader so future schema migrations can be introduced.

---

# 4. Workspace Configuration

Support defining one or more workspaces.

Example:

```toml
[[workspaces]]
id = "project-x"
name = "Project X"
root = "~/Projects/project-x"
```

A workspace should be able to contain or reference:

- Services
- Libraries
- Groups
- Profiles
- Environment configuration

Avoid duplicating the same service configuration across profiles or groups.

---

# 5. Service Configuration

Define a configuration model for services.

Example:

```toml
[[services]]
id = "auth-service"
name = "auth-service"
type = "backend"
workspace = "project-x"
path = "backend/auth-service"
default_branch = "master"
```

Support service types such as:

```text
backend
frontend
library
```

Do not implement service-specific behavior using service names.

---

# 6. Repository Configuration

Support repository information.

Example:

```toml
[services.repository]
url = "git@github.com:company/auth-service.git"
```

Potential fields:

```text
url
default_branch
```

Do not implement Git operations yet.

---

# 7. Runtime Configuration

Support runtime requirements.

Backend example:

```toml
[services.runtime]
type = "java"
version = "21"
```

Frontend example:

```toml
[services.runtime]
type = "node"
version = "20.19.4"
```

The configuration should be extensible to future runtimes.

Do not implement runtime discovery in this task.

---

# 8. Command Configuration

Support service-specific commands.

Example:

```toml
[services.commands]
install = "./mvnw dependency:resolve"
build = "./mvnw clean install"
start = "./mvnw spring-boot:run"
```

Frontend:

```toml
[services.commands]
install = "npm install"
build = "npm run build"
start = "npm start"
```

Important:

Do not immediately execute arbitrary commands.

This task only defines and validates command configuration.

Execution and security policies will be implemented later.

Where feasible, design the command model so structured command arguments can eventually be supported.

# 12. Dependencies

Support service dependencies.

Example:

```toml
[services.dependencies]
services = ["auth-service"]
libraries = ["common-core"]
```

or another clean representation if preferred.

Do not implement dependency resolution yet.

Only model and validate references.

Validation should detect:

- Unknown service
- Unknown library
- Self-dependency where invalid
- Duplicate dependencies

Circular dependency detection can be implemented here or later, but document the decision.

---

# 13. Libraries

Define library configuration.

Example:

```toml
[[libraries]]
id = "common-core"
name = "common-core"
workspace = "project-x"
path = "libraries/common-core"
type = "maven"

[libraries.repository]
url = "git@github.com:company/common-core.git"

[libraries.commands]
build = "./mvnw clean install"
```

Support artifact metadata:

```toml
[libraries.artifact]
group_id = "com.company"
artifact_id = "common-core"
version = "1.8.0-SNAPSHOT"
```

---

# 14. Service Groups

Support logical service groups.

Example:

```toml
[[groups]]
id = "customer"
name = "Customer Management"
services = [
  "auth-service",
  "user-service",
  "customer-service"
]
```

Validate that all referenced services exist.

Do not duplicate service definitions inside groups.

---

# 15. Profiles

Support developer profiles.

Example:

```toml
[[profiles]]
id = "backend-development"
name = "Backend Development"
services = [
  "auth-service",
  "user-service",
  "customer-service"
]
```

Profiles should reference services or groups.

Do not duplicate configuration.

# 16. Execution Configuration

Possible future settings:


---

# 17. Environment Configuration

The configuration system should support service-specific environment variables.

Example:

```toml
[services.environment]
SPRING_PROFILES_ACTIVE = "local"
SERVER_PORT = "8081"
```

Important:

Do not persist or display secrets as plaintext.

Consider supporting:

```text
literal
environment reference
secret reference
```

as separate concepts in the future.

For MVP, environment values can be modeled simply, but document how the design could evolve.

---

# 18. Path Resolution

Paths may use:

```text
~/Projects/project-x
```

or relative paths:

```text
backend/auth-service
```

The configuration layer should normalize paths relative to the workspace root where appropriate.

Do not perform filesystem mutations yet.

Do not assume repositories already exist.

---

# 19. Validation

Implement configuration validation.

Validation should detect at least:

### Structural

- Missing required fields
- Invalid enum values
- Invalid version
- Invalid data types

### References

- Unknown workspace
- Unknown service
- Unknown library
- Unknown group
- Unknown profile

### Paths

- Empty paths
- Invalid path structure where detectable

### Ports

- Out-of-range ports
- Duplicate ports where conflicts are invalid

### Dependencies

- Unknown references
- Duplicate references
- Invalid self-dependencies

### Commands

- Empty required commands
- Invalid command representation

### Configuration consistency

Examples:

- Frontend service without a valid runtime
- Backend service without build/start configuration where required
- Library without artifact metadata when artifact metadata is required
- Health check with missing required fields

Do not over-validate assumptions that are not explicitly required.

Validation should remain practical.

---

# 20. Configuration Errors

Configuration errors must be actionable.

Bad:

```text
Invalid configuration
```

Good:

```text
Configuration validation failed.

File:
~/.service-orchestrator/config.toml

Location:
services[2].runtime.version

Problem:
Node runtime version is missing.

Expected:
A non-empty semantic/version-like string.

Suggested fix:
Set:

[services.runtime]
type = "node"
version = "20.19.4"
```

Whenever practical, include:

- File
- Section
- Field
- Problem
- Suggested fix

---

# 21. Unknown Fields

Decide how unknown TOML fields should be handled.

Prefer a strict configuration model for critical sections so typos are not silently ignored.

Example:

```text
max_parallel_tasks
```

vs accidental:

```text
max_paralel_tasks
```

A typo should preferably produce a useful validation error.

Document the chosen behavior.

---

# 22. Defaults

Provide reasonable defaults where they are safe.

Example:

```text
config_version = 1
max_parallel_tasks = 4
```

Do not provide defaults that could cause destructive or surprising behavior.

---

# 23. Configuration API

Create a clean API for loading configuration.

Conceptually:

```rust
pub trait ConfigLoader {
    fn load(&self, path: &Path) -> Result<Config>;
}
```

The exact abstraction may differ if another design is better.

The application should not directly parse TOML everywhere.

---

# 24. Configuration Sources

The initial implementation only needs TOML file support.

However, design the configuration loading boundary so future sources could be added:

```text
TOML
Environment variables
CLI overrides
Team-shared configuration
Remote configuration
```

Do not implement those future sources now.

---

# 25. Configuration Merge Strategy

Do NOT implement complex configuration merging unless required.

If the architecture anticipates future overrides, document where merging would occur.

Do not build a generalized configuration engine for hypothetical use cases.

---

# 26. Serialization

Use `serde` for TOML serialization/deserialization.

Separate:

```text
Raw TOML models
```

from:

```text
Validated application/domain configuration
```

where this separation improves maintainability.

# 31. Crate Responsibilities

Keep configuration-specific code in the configuration crate.

For example:

```text
crates/config/
├── src/
│   ├── lib.rs
│   ├── loader.rs
│   ├── raw.rs
│   ├── validation.rs
│   ├── normalize.rs
│   └── error.rs
```

The exact structure can differ if a cleaner design is justified.

Do not put configuration parsing into:

```text
domain
tui
mcp
git
process
```

---

# 32. Domain Independence

The domain crate must remain independent from TOML.

Do not create domain models that directly encode TOML-specific behavior.

The desired flow is:

```text
TOML
  ↓
Raw Configuration Model
  ↓
Validation
  ↓
Normalized Configuration
  ↓
Domain/Application Model
```
