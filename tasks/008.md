# Task 008 — Build Manager Architecture Amendment

Before implementing Task 008, apply the following architectural requirements.

## Core Requirement

The Build Manager must be **build-system agnostic**.

Maven is the primary build system used by the current backend services, but the architecture must not be coupled to Maven.

The initial concrete implementations should be:

- MavenBuildProvider
- NpmBuildProvider

Gradle support is explicitly planned for the future.

Do not implement GradleBuildProvider in this task.

## Build Provider Abstraction

Introduce a focused `BuildProvider` abstraction using idiomatic Rust.

The provider should be responsible for:

- Declaring supported capabilities
- Validating build-system-specific requirements
- Resolving the appropriate executable or wrapper
- Constructing structured build plans
- Providing build-system-specific error context

The provider should not directly spawn processes or schedule tasks.

The Task Engine and Process Manager must remain responsible for execution.

## Build Operations

Use build-system-neutral operations where their semantics are genuinely shared.

Examples:

- Clean
- Build
- Test
- InstallDependencies
- PublishLocalArtifact

Do not assume every build provider supports every operation.

In particular, Maven `install`, Gradle `publishToMavenLocal`, and npm dependency installation have different semantics.

Unsupported operations must return explicit structured errors.

## Provider Registry

Implement a small registry or resolver that selects a provider based on validated service configuration.

Avoid a large plugin framework.

Register Maven and npm providers initially.

Adding Gradle later should primarily require:

1. Implementing `GradleBuildProvider`.
2. Registering the provider.
3. Extending configuration validation where necessary.
4. Adding provider-specific tests.

It should not require rewriting the Build Manager, Task Engine, Application Core, TUI, or MCP.

## Build Plans

Providers should generate structured build plans rather than execute shell commands directly.

A build plan should contain:

- Executable
- Arguments
- Working directory
- Environment requirements
- Timeout
- Expected outputs where appropriate

The existing Process Manager must execute the resulting commands.

## Configuration

Build-system selection must be configuration-driven.

Support Maven and npm in the current implementation.

Design the schema so Gradle can be introduced without breaking existing configurations.

Do not add an unimplemented Gradle option that appears operational to users.

## Tests

In addition to the original Task 008 tests, verify:

- Maven provider selection
- npm provider selection
- Unknown provider rejection
- Unsupported operation handling
- Build plan generation
- Provider-independent orchestration
- No direct process spawning from providers

## Architecture Documentation

Update the Build Manager ADR and architecture documentation to explain:

- Why a provider abstraction exists
- Why Maven is the primary implementation
- How Gradle can be added later
- Why capabilities differ between providers
- Why providers generate plans instead of executing processes

## Important

Do not create a generalized plugin framework.

Do not implement Gradle yet.

Do not duplicate scheduling or process management.

Keep the abstraction minimal, testable, and extensible.

**The goal is Maven-first implementation with build-system-independent architecture.**
