# Task 026 — Security Hardening & Permission Management

## Role

Act as a Principal Rust Security Engineer, Application Security Architect, macOS Systems Security Engineer, and Secure Developer Tooling Engineer.

You are implementing **Task 026 — Security Hardening & Permission Management** of the Service Orchestrator project.

Your objective is to perform a comprehensive security review and implement targeted security improvements across the existing local developer orchestration platform.

This is a single, end-to-end security engineering task.

Do not stop after planning. Inspect, identify vulnerabilities, implement fixes, test, document, and report the completed work.

---

# 1. Execution Strategy

Follow these rules throughout the task:

- Read `AGENTS.md` completely.
- Read documentation relevant to the affected modules.
- Inspect actual implementations before making changes.
- Identify concrete security risks rather than inventing hypothetical vulnerabilities.
- Prioritize exploitable vulnerabilities and unsafe behavior.
- Preserve the existing architecture.
- Reuse existing policy and authorization mechanisms.
- Avoid unrelated refactoring.
- Run focused tests during implementation.
- Run full validation at completion.
- Maintain a concise progress record in `docs/task-026-progress.md` if useful for context recovery.
- Work autonomously through safe implementation and testing.
- Request approval before destructive, sensitive, or externally impactful operations.

**Do not stop after producing a security report. Implement and verify justified security fixes.**

# 2. Project Context

Service Orchestrator is a local macOS developer orchestration platform.

It consists of:

- Rust Application Core
- Shared Local Daemon
- Tokio Task Engine
- Workflow Engine
- Git Manager
- Build Manager
- Library Manager
- Migration Manager
- Process Manager
- Service Runtime
- Health Manager
- Observability
- Unix Domain Socket IPC
- Ratatui TUI
- MCP Server
- Tauri 2 + React + TypeScript GUI

The application is intended for local development use.

It does not require a remote backend or an LLM.

The MCP interface allows AI agents to request operations, but all operations must remain subject to the same application security policies.

# 4. Threat Model

Create a practical threat model for the application.

Consider:

- Malicious or malformed MCP requests
- Untrusted AI-generated tool arguments
- Compromised local processes
- Unauthorized local IPC clients
- Malicious repository paths
- Symlink attacks
- Git argument injection
- Shell command injection
- Credential leakage
- Unsafe database migrations
- Unauthorized process termination
- Configuration tampering
- Dependency supply-chain risks

Distinguish realistic threats from low-probability theoretical concerns.

Do not assume that running locally eliminates security risks.

---

# 5. Trust Boundaries

Document trust boundaries.

```text
React GUI ─────┐
               │
Ratatui TUI ───┼──► Local IPC ──► Shared Daemon
               │                      │
MCP Server ────┘                      ▼
                               Application Core
                                      │
                                Policy Engine
                                      │
                                Infrastructure
```

The daemon must enforce authorization.

Do not trust a client simply because it connects through a local Unix Domain Socket.

---

# 6. Security Invariants

The following must remain true:

1. All privileged operations pass through Application Core.
2. All interfaces use the same policy engine.
3. MCP cannot bypass security restrictions.
4. No arbitrary shell execution is exposed by default.
5. Destructive Git operations require authorization.
6. Database migrations require target-aware policy checks.
7. Unrelated OS processes must never be terminated.
8. Secrets must not be exposed through logs or API responses.
9. Configuration changes must be validated.
10. Untrusted input must never be interpolated into shell commands.

---

# 7. Local IPC Security

Review Unix Domain Socket security.

Verify:

- Private runtime directory
- Restrictive directory permissions
- Restrictive socket permissions
- Safe socket creation
- Safe stale-socket cleanup
- Peer identity validation where supported
- Protocol version validation
- Message size limits
- Connection limits
- Request timeouts

Avoid public TCP listeners.

Do not expose the daemon over the network.

---

# 8. IPC Peer Identity

Evaluate macOS-supported peer credential mechanisms.

Where practical, verify that connecting clients belong to the expected local user.

Do not rely exclusively on the socket path.

Document the limits of same-user authentication.

Do not invent a complex multi-user authentication system.

---

# 9. IPC Request Validation

Validate all incoming IPC requests.

Check:

- Protocol version
- Operation name
- Request ID
- Payload schema
- Required fields
- Resource identifiers
- Maximum message size
- Maximum collection sizes

Malformed requests must not crash the daemon.

---

# 10. IPC Authorization

Every mutating request must pass through the shared policy engine.

Do not authorize based solely on:

- Client type
- TUI origin
- GUI origin
- MCP origin
- A frontend confirmation boolean

Use trusted authorization context.

---

# 11. Permission Model

Review the existing permission model.

At minimum distinguish:

- Read
- SafeWrite
- Destructive

Extend the model only where real requirements justify it.

Consider additional risk attributes:

- Target environment
- Resource type
- Operation scope
- Database mutation
- Filesystem mutation
- Process termination

Avoid an unnecessarily complicated role-based access-control system.

---

# 12. Operation Classification

Audit operation classifications.

Examples:

| Operation | Risk |
|---|---|
| List services | Read |
| Git status | Read |
| Git fetch | SafeWrite |
| Git checkout | SafeWrite with preconditions |
| Git reset --hard | Destructive |
| Build service | Mutating execution |
| npm install | Mutating execution |
| Start service | Mutating execution |
| Stop managed service | Mutating execution |
| Liquibase status | Read-oriented |
| Liquibase update | Database mutation |
| Remove workspace files | Destructive |

Do not assume all SafeWrite operations are harmless.

Maven plugins and npm scripts may execute arbitrary project code.

---

# 13. Authorization Flow

Review the existing authorization mechanism.

Required properties:

- Explicit operation identity
- Explicit resource scope
- Explicit risk classification
- Trusted authorization context
- Clear denial behavior
- Auditability

Do not accept `confirmed: true` as sufficient authorization.

If a secure authorization flow is unavailable, protected operations must fail closed.

---

# 14. MCP Security

Review all exposed MCP tools.

Verify:

- Strict input schemas
- Correct resource scoping
- No unrestricted shell tools
- No unrestricted filesystem tools
- No arbitrary database execution
- Bounded responses
- Policy enforcement
- Secret redaction
- Safe error messages

Do not trust AI-generated tool arguments.

---

# 15. MCP Prompt Injection

Treat repository files, logs, build output, and external command output as untrusted data.

AI agents may encounter malicious instructions inside these sources.

Ensure MCP tool descriptions and outputs clearly distinguish application data from instructions.

Do not allow untrusted content to modify authorization decisions.

Do not implement an LLM-based authorization mechanism.

---

# 16. MCP Tool Results

Audit MCP responses for sensitive information.

Potential leakage sources:

- Environment variables
- Git remote URLs
- Maven settings
- npm registry credentials
- Database connection strings
- Process arguments
- Build logs
- Error messages

Redact sensitive values before returning data.

---

# 17. Tauri Security

Review Tauri 2 capabilities and permissions.

Verify:

- Minimal capabilities
- Restricted command exposure
- No unrestricted shell plugin
- No unnecessary filesystem access
- Restricted external navigation
- Safe window/webview behavior
- Input validation
- Safe event payloads

Do not grant broad permissions merely to simplify implementation.

---

# 18. Frontend Trust Boundary

React is not a trusted authorization boundary.

Frontend validation improves UX but must not replace backend validation.

All privileged operations must be validated by the daemon.

Do not embed secrets in frontend bundles.

---

# 19. Filesystem Path Safety

Audit path handling.

Protect against:

- Path traversal
- Unexpected absolute paths
- Symlink escape
- Invalid workspace roots
- Repository path confusion
- Unsafe temporary file handling
- TOCTOU risks where relevant

Use canonicalization carefully.

Do not assume paths always exist before repository cloning.

---

# 20. Workspace Isolation

Ensure operations affect only explicitly configured and authorized workspaces.

Do not allow arbitrary filesystem paths to be passed through MCP or IPC as substitutes for validated resource identifiers.

Use workspace-aware IDs.

---

# 21. Git Security

Audit Git operations.

Verify:

- Structured arguments
- Branch validation
- Option injection prevention
- Working-tree protection
- Safe checkout
- Fast-forward-only pull defaults
- Explicit destructive authorization
- Safe repository path resolution

Do not silently reset or clean repositories.

---

# 22. Git Authentication

Respect existing developer Git authentication.

Do not store SSH private keys or tokens.

Avoid logging credential-bearing URLs.

Do not disable SSH host verification automatically.

Do not configure insecure Git credential helpers.

---

# 23. Git Hooks

Recognize that Git operations may trigger hooks or configured external commands.

Do not assume Git operations are always side-effect free.

Document trust assumptions for developer-controlled repositories.

Do not silently disable security protections.

---

# 24. Build Execution Security

Audit Maven and npm execution.

Verify:

- Structured executable arguments
- Validated working directories
- Configured commands
- Safe environment handling
- No uncontrolled shell interpolation
- Correct timeout and cancellation behavior

Do not claim builds are sandboxed.

Maven plugins and npm scripts can execute arbitrary code.

---

# 25. Build Provider Security

Review the BuildProvider abstraction.

Ensure providers cannot bypass the Process Manager or application policy checks.

Do not introduce unrestricted command execution through provider configuration.

---

# 26. Dependency Supply Chain

Review Rust and frontend dependencies.

Use available auditing tools where appropriate.

Examples:

- Rust dependency advisories
- npm audit
- Tauri dependency security
- Lockfile integrity

Do not automatically apply breaking dependency upgrades.

Report findings and implement safe, compatible updates where justified.

# 27. Database Migration Security

Audit Migration Manager behavior.

Verify:

- Target identification
- Environment classification
- Authorization
- Database-scoped coordination
- No automatic retries after partial failure
- No automatic rollback claims
- No automatic Liquibase lock release
- Credential redaction

Do not execute migrations against real shared or production databases during testing.

---

# 28. Localhost Safety

Do not assume localhost means a local database.

A local tunnel may connect to a remote database.

Database target classification must use validated configuration and explicit policy.

---

# 29. Process Ownership

Audit Process Manager and Service Runtime.

Ensure:

- Only managed processes can be stopped.
- PID reuse is handled safely.
- Process identity is validated.
- Process groups are handled correctly.
- Unrelated processes are not terminated.
- Cancellation cleanup is reliable.

Do not kill processes solely because they occupy a configured port.

---

# 30. Daemon Lifecycle Security

Review:

- Automatic startup
- Single-instance enforcement
- Stale socket cleanup
- Daemon shutdown
- Unexpected termination
- Process recovery
- Client reconnection

Prevent duplicate authoritative daemons.

Do not adopt unrelated processes based only on PID or port.
