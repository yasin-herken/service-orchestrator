# Goal

Define the core domain model and core contracts for Service Orchestrator.

Do NOT implement Git, Maven, Node, Liquibase, process execution, MCP, or Ratatui yet.

The goal is to establish the vocabulary and contracts that all future modules will use.

The domain model must remain independent from infrastructure and UI concerns.

---

# 1. Domain Concepts

Define the core entities/value objects needed for the platform.

At minimum consider:

```text
Workspace
Service
Repository
Library
Profile
ServiceGroup
Dependency
Task
Workflow
Runtime
HealthCheck
Port
Environment
GitState
ProcessState
Permission
```

Do not blindly create all of these as large structs.

Use the smallest useful model.

Prefer domain types that represent real concepts in the system.

---

# 2. Service Model

Define a service model capable of representing:

- Backend services
- Frontend applications
- Libraries
- Future service types

For example, the model may conceptually contain:

```text
Service
├── id/name
├── type
├── repository
├── path
├── runtime
├── commands
├── dependencies
├── health checks
├── ports
└── metadata
```

Service type should be extensible.

Do not create business logic based on service names.

Avoid code patterns such as:

```rust
if service.name == "auth-service" {
    ...
}
```

Behavior must be based on type, capabilities, or configuration.

---

# 3. Service Type

Define a strongly typed service category.

At minimum support:

```text
Backend
Frontend
Library
```

The design should make future types possible without changing unrelated parts of the system.

---

# 4. Repository Model

Represent source-control information independently from the Git implementation.

The domain model should not depend directly on `git2`, Git CLI types, or OS process types.

Possible concepts:

```text
Repository
├── url
├── local_path
├── default_branch
└── provider metadata
```

Do not implement Git behavior yet.

---

# 5. Runtime Model

Represent runtime requirements without tying them to a specific executable implementation.

Examples:

```text
Java 21
Node 20.19.4
Maven
npm
```

A runtime should describe what the service requires, not how the executable is discovered.

Runtime discovery will be implemented later.

---

# 6. Command Model

Services need configurable commands such as:

```text
build
start
stop
restart
install
test
liquibase
```

Do not store arbitrary business behavior in the command model.

The model should allow future command types without forcing infrastructure details into the domain.

Consider using a structured representation rather than only raw shell strings.

Security requirements from `AGENTS.md` must be respected.

---

# 7. Dependency Model

Define a dependency relationship between services and libraries.

For example:

```text
common-core -> auth-service
auth-service -> user-service
```

The model should support dependency-aware scheduling later.

Avoid implementing the scheduler at this stage.

The domain model should be capable of representing:

- Direct dependencies
- Dependency type where needed
- Optional future metadata

---

# 8. Task Model

Define the domain representation of a task.

At minimum support:

```text
Queued
Running
Succeeded
Failed
Cancelled
Skipped
Blocked
```

A task should have enough metadata to support future execution and UI/MCP reporting.

Consider:

```text
Task
├── id
├── type
├── status
├── service
├── workflow
├── timestamps
├── progress
├── error
└── dependencies
```

Do not implement task execution yet.

---

# 9. Workflow Model

Represent a workflow independently from its executor.

Example:

```text
PrepareEnvironment
    ├── SyncRepositories
    ├── BuildLibraries
    ├── RunLiquibase
    ├── BuildServices
    ├── StartServices
    └── HealthChecks
```

The workflow model should support:

- Tasks
- Dependencies
- Execution order
- Future conditions
- Future retry policies

Do not implement the scheduler yet.

---

# 10. Profile Model

Represent developer profiles.

Example:

```text
backend-development
payment-development
full-stack
```

A profile should reference services/groups rather than duplicate their definitions.

Example conceptual model:

```text
Profile
├── id
├── name
└── service references
```

---

# 11. Service Group Model

Represent logical groups of services.

Example:

```text
Customer
    auth-service
    user-service
    customer-service
```

A group should reference services rather than duplicate service definitions.

---

# 12. Health Check Model

Define a generic health check model.

Possible types:

```text
Process
Port
HTTP
```

Do not implement HTTP/process checks yet.

The model should allow future additions such as:

```text
Docker
Kubernetes
Spring Actuator
```

---

# 13. Process State

Represent the logical state of a local process.

At minimum:

```text
NotRunning
Starting
Running
Stopping
Stopped
Failed
Unknown
```

Do not store OS-specific process implementation details in the domain.

PID management belongs to the process infrastructure layer.

---

# 14. Git State

Represent Git state in a provider-independent way.

For example:

```text
Clean
Modified
Ahead
Behind
Diverged
Unknown
```

The exact model can be improved based on the architecture.

The domain must not depend on a specific Git library.

---

# 15. Permission Model

Define permission/risk levels for operations.

At minimum:

```text
Read
SafeWrite
Destructive
```

This will later be used by both:

- TUI
- MCP

The policy engine must be interface-independent.

For example:

```text
git_status      -> Read
git_pull        -> SafeWrite
git_reset       -> Destructive
```

Do not implement the full policy engine yet.

Only establish the domain contract.

---

# 16. IDs

Use strongly typed IDs where appropriate.

Potential IDs:

```text
ServiceId
WorkspaceId
TaskId
WorkflowId
ProfileId
LibraryId
```

Avoid passing arbitrary strings everywhere when a real domain identifier exists.

Do not overdo this.

Use strong types where they provide actual value.

---

# 17. Time

Use appropriate domain representations for timestamps.

Avoid scattering raw timestamp primitives throughout the domain model.

Use a consistent approach.

---

# 18. Error Model

Define the initial domain/application error strategy.

Distinguish between:

```text
Validation errors
Domain errors
Application errors
Infrastructure errors
```

Do not introduce an enormous global error enum.

Keep the domain errors small and meaningful.

---

# 19. Traits and Interfaces

Define only interfaces that represent real boundaries.

Potential future boundaries include:

```text
GitProvider
ProcessExecutor
BuildExecutor
HealthChecker
Logger
```

However:

IMPORTANT:

Do not implement infrastructure interfaces unless needed by the current task.

The goal is to establish contracts, not create a speculative framework.

---

# 20. Serialization

Determine which domain types should be serializable.

Configuration-oriented models will eventually need serialization/deserialization.

However, avoid coupling every domain type to serialization unless there is a reason.

Where serialization is necessary, use `serde`.

---

# 21. Crate Boundaries

Keep the domain crate independent.

The intended dependency direction should remain approximately:

```text
tui ───────┐
           │
mcp ───────┼──> application ───> domain
           │
future cli ┘

infrastructure
      │
      ▼
application
```

The domain crate must not depend on:

```text
ratatui
rmcp
git2
tokio
reqwest
OS-specific process APIs
```

unless a concrete, well-justified requirement exists.

---

Group related concepts where that produces a cleaner design.
