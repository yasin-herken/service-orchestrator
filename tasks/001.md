Read `AGENTS.md` completely before doing anything else.

We are starting the Service Orchestrator project.

Your task is to establish the initial project foundation and architecture documentation.

Do NOT implement the actual service management logic yet.

## Goal

Create the initial repository structure and establish a clear architectural foundation for the project.

The project is a macOS-native Rust application with:

- Ratatui TUI
- MCP server
- Shared application core
- Git management
- Build orchestration
- Library management
- Liquibase execution
- Process management
- Health checks
- Logs
- Task/workflow engine

The most important architectural constraint is:

> The application core must not depend on Ratatui or MCP. Both are interface adapters over the same application core.

## Tasks

### 1. Inspect the repository

First inspect the current repository.

Do not assume the repository is empty.

Identify:

- Existing files
- Existing Rust code
- Existing Cargo configuration
- Existing documentation
- Existing CI configuration
- Existing conventions

Preserve useful existing work.

### 2. Create the initial Rust project structure

Create a clean Cargo workspace suitable for the architecture described in `AGENTS.md`.

Prefer a modular structure such as:

```text
crates/
├── domain/
├── application/
├── config/
├── execution/
├── git/
├── process/
├── build/
├── liquibase/
├── health/
├── logging/
├── policy/
├── mcp/
└── tui/
```

Do not create unnecessary implementations yet.

At this stage, establish the crate boundaries and minimal compileable structure.

### 3. Define dependency direction

Document and enforce the intended dependency direction.

The conceptual dependency flow should be:

```text
Interfaces
    ↓
Application
    ↓
Domain

Infrastructure
    ↑
Application
```

More concretely:

```text
tui ───────┐
           │
mcp ───────┼──> application ───> domain
           │
future cli ┘

application ───> infrastructure abstractions

infrastructure implementations
    ├── git
    ├── process
    ├── build
    ├── liquibase
    ├── health
    └── logging
```

Do not allow:

```text
domain -> tui
domain -> mcp
application -> ratatui
domain -> git2
domain -> tokio-specific implementation details
```

unless there is a compelling reason.

### 4. Create architecture documentation

Create:

```text
docs/architecture.md
```

It must explain:

- Product purpose
- Architectural layers
- Crate responsibilities
- Dependency direction
- Why TUI and MCP are adapters
- Why the core must work without an LLM
- Where future CLI/API interfaces would fit
- Where service executors belong
- Where the task engine belongs

Include an architecture diagram using plain text/ASCII.

### 5. Create an initial ADR

Create:

```text
docs/adr/001-core-architecture.md
```

Document the decision:

> Core-first architecture with TUI and MCP as adapters.

Include:

- Context
- Decision
- Alternatives considered
- Reasoning
- Consequences

### 6. Do not implement yet

Do NOT implement:

- Git operations
- Maven execution
- npm execution
- Liquibase
- Process management
- MCP tools
- Ratatui screens
- Scheduler
- Task execution

Only establish the project foundation and architecture.

### 7. Validation

After making the changes, run:

```bash
cargo fmt --check
cargo check --workspace
cargo test --workspace
cargo clippy --workspace --all-targets --all-features -- -D warnings
```

Fix any issues caused by your changes.
