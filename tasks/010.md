# 2. Goal

Implement a production-quality **Service Runtime Management** layer.

This component must manage the local execution lifecycle of backend and frontend services.

Initial implementations:

- Java/Spring Boot Runtime
- Node.js/React Runtime

The architecture must remain extensible to future runtimes such as:

- Python
- Go
- Docker
- Kubernetes

Do not implement these future runtimes yet.

The Service Runtime layer must remain independent from Ratatui and MCP.

---

# 3. Architectural Principle

Separate service runtime behavior from process execution.

The Service Runtime determines:

- How a service should start
- Which runtime is required
- Which command should be used
- Which working directory is required
- Which environment variables should be provided
- How startup should be interpreted
- Which stop strategy applies

The Process Manager determines:

- How processes are spawned
- How processes are tracked
- How signals are delivered
- How processes are terminated
- How stdout/stderr are captured

The Task Engine determines:

- When operations execute
- How operations are scheduled
- How cancellation propagates
- How task state is tracked

Do not duplicate these responsibilities.

# 5. Runtime Abstraction

Introduce a focused, idiomatic Rust runtime abstraction.

Conceptually:

```rust
pub trait ServiceRuntime: Send + Sync {
    fn runtime_type(&self) -> RuntimeType;

    fn validate(
        &self,
        service: &Service,
    ) -> Result<(), RuntimeError>;

    fn prepare_start(
        &self,
        service: &Service,
    ) -> Result<ProcessSpecification, RuntimeError>;

    fn stop_strategy(
        &self,
        service: &Service,
    ) -> StopStrategy;
}
```

This is an example, not a mandatory API.

Adapt to existing domain and process abstractions.

Prefer runtime implementations that produce structured process specifications rather than spawning processes directly.

Do not introduce unnecessary methods or abstractions.

# 14. Start Idempotency

Starting an already-running service must not create a duplicate process.

Expected behavior:

```text

    |

Already running
    |
    v
Return existing runtime state
```

Concurrent start requests must be coordinated.

Example:

```text
TUI: Start auth-service
MCP: Start auth-service
```

Only one managed service process should be created.

Reuse existing operation coordination where appropriate.

# 19. Long-Running Service Processes

This requirement is critical.

A service process may run for hours.

Do not keep its startup task permanently running.

Separate:

1. Startup operation lifecycle
2. Managed service process lifecycle

For example:

```text
StartService Task
       |
       v
Spawn Process
       |
       v
Confirm Process Started
       |
       v
Task Succeeded

Managed Service Process
       |
       v
Continues Running
       |
       v
Eventually Stopped
```

The Task Engine must not treat a successfully started long-running service as an unfinished task.

Document the ownership and lifetime of managed processes.

- Workspace
- Service ID
- Process ID
- Process handle
- Start timestamp
- Current state
- Startup command identity
- Exit information

Do not terminate unrelated processes simply because they use the same port.

Do not assume every process found on a configured port belongs to Service Orchestrator.

# 25. Unexpected Process Exit

1. Detect the exit.
2. Update runtime state.
3. Preserve exit information.
4. Emit a runtime event.

# 26. Cancellation Semantics

Distinguish between:

- Cancelling a pending startup task
- Cancelling a startup in progress
- Stopping an already-running service

Cancelling a startup must not leave an untracked process behind.

After a service has successfully started, cancelling the completed startup task must not stop the service.

Stopping the service requires an explicit StopService operation.
