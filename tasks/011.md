# 3. Architectural Principles

The Migration Manager determines:

- Which migration provider is required
- Which migration operation is requested
- Which service/database configuration applies
- Which migration steps should execute
- Which safety policy applies

The MigrationProvider determines:

- Provider-specific capabilities
- Required executable or build tool
- Structured command arguments
- Migration-specific validation
- Provider-specific output interpretation

The Task Engine determines:

- Scheduling
- Dependencies
- Concurrency
- Task lifecycle
- Cancellation
- Timeouts

The Process Manager determines:

- Process spawning
- stdout/stderr capture
- Process termination
- Exit detection

Do not duplicate these responsibilities.

# 4. Migration Provider Abstraction

Introduce a focused Rust abstraction.

Conceptually:

```rust
pub trait MigrationProvider: Send + Sync {
    fn provider_type(&self) -> MigrationProviderType;

    fn capabilities(&self) -> MigrationCapabilities;

    fn validate(
        &self,
        context: &MigrationContext,
    ) -> Result<(), MigrationError>;

    fn prepare(
        &self,
        request: &MigrationRequest,
    ) -> Result<MigrationPlan, MigrationError>;
}
```

This is illustrative, not a mandatory API.

Reuse existing abstractions and conventions.

Providers must generate structured execution plans.

Providers must not directly spawn OS processes.

# 10. Environment Safety

The initial implementation is intended for local development.

Default policy:

**Only explicitly configured local development targets may execute migrations automatically.**

Shared development, staging, and production environments must not be silently migrated.

For non-local targets:

- Require explicit authorization.
- Clearly identify the target.
- Require confirmation through the shared policy layer.
- Reject execution when authorization cannot be verified.

Do not infer that a database is safe merely because its hostname contains `localhost`.

Local port forwarding and tunnels may point to remote databases.

# 14. Apply Migration Workflow

Implement a high-level migration workflow.

```text
ApplyMigration
      │
      ▼
Validate Service
      │
      ▼
Resolve Provider
      │
      ▼
Validate Database Target
      │
      ▼
Check Authorization
      │
      ▼
Validate Migration Configuration
      │
      ▼
Acquire Database Migration Lock
      │
      ▼
Execute Migration
      │
      ▼
Capture Result
      │
      ▼
Release Lock
      │
      ▼
Complete
```

Do not assume every migration is reversible.

Do not automatically retry failed migrations.

# 15. Database-Level Concurrency

Multiple services may share the same database.

This is particularly important for the current microservice architecture.

Example:

```text
auth-service ─────┐
                  ├── shared-development-db
user-service ─────┘
```

Do not allow conflicting migrations against the same configured database target to execute concurrently.

Introduce or reuse a database-target-scoped operation coordination mechanism.

Independent database targets may execute concurrently.

Use Liquibase's own database locking as an additional safety mechanism, not as a substitute for application-level coordination.

Document the limitation that an in-process lock does not coordinate independent Service Orchestrator instances.

---

# 16. Liquibase Lock Handling

Liquibase uses database locking to coordinate changeset execution.

The implementation should recognize common lock-related failures.

Do not automatically release Liquibase database locks.

Do not automatically modify Liquibase tracking tables.

Provide actionable diagnostics for lock-related failures.

Any future force-release capability must require explicit authorization and separate implementation.

---

# 17. Migration Failure Handling

A failed migration must:

- Mark the task as failed.
- Preserve relevant exit information.
- Capture logs.
- Prevent dependent startup workflow steps from proceeding.
- Report the affected service and database target.
- Avoid claiming the database was rolled back.

Database migration operations are not necessarily atomic across all changesets or database platforms.

Document partial-application risks.

---

# 18. Cancellation Semantics

Migration cancellation must integrate with the Task Engine and Process Manager.

However, cancellation of the external process does not guarantee that database changes have been rolled back.

After cancellation:

- Stop the managed process according to existing policy.
- Record cancellation.
- Mark database state as requiring reinspection where appropriate.
- Do not automatically rerun the migration.
- Do not claim rollback without verification.

---

# 19. Retry Policy

Automatic retry must be disabled by default for migration execution.

A failed migration may have partially modified the database.

Retries should require an explicit new operation after inspecting current migration status.

Read-only inspection operations may use a different retry policy where safe.
