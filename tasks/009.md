# 4. Library as a First-Class Domain Concept

A library is not simply another backend service.

Libraries have additional responsibilities:

- Artifact identity
- Artifact version
- Local installation
- Dependency relationships
- Build ordering
- Consumer compatibility

Reuse the existing library domain model.

Extend it only when necessary.

A Maven library should be identifiable through coordinates such as:

```text
groupId
artifactId
version
packaging
classifier (optional)
```

Example:

```text
com.company:common-core:1.8.0-SNAPSHOT
```

Do not identify Maven artifacts using only repository names.

# 11. Library Version Management

This is a critical requirement.

Developers must be able to build a local library version and use it in dependent services.

Example:

```text
Library:
common-core

Version:
1.8.0-SNAPSHOT

Dependent services:
auth-service
user-service
payment-service
```

The system should support selecting a configured library version and determining whether dependent services reference compatible coordinates.

Do not assume installing an artifact locally automatically changes the dependency version used by every consumer.

Version alignment must be explicit.

# 12. Maven Dependency Version Sources

A Maven dependency version may be defined through:

- Direct dependency version
- Maven property
- Parent POM
- Dependency management
- Imported BOM
- Multi-module reactor configuration

The implementation must not assume that every dependency version is a direct XML element in the consuming service's `pom.xml`.

Do not use naive text replacement to modify Maven POM files.

---

# 13. Safe Version Override Strategy

Implement a conservative version management approach.

For MVP:

1. Inspect the configured dependency relationship.
2. Determine the expected artifact coordinates.
3. Detect the effective or configured dependency version where reliably possible.
4. Compare it with the locally installed library version.
5. Report mismatches.
6. Provide a structured version alignment plan.

Do not silently rewrite POM files.

If automatic version modification is implemented, it must:

- Be explicitly requested
- Support a preview/dry-run
- Preserve unrelated POM content
- Require appropriate authorization
- Be reversible
- Have integration tests

Prefer deferring automatic POM modification rather than implementing an unsafe solution.

# 14. Library Version Alignment Plan

Provide a structured result.

Example:

```json
{
  "library": "common-core",
  "targetVersion": "1.8.0-SNAPSHOT",
  "consumers": [
    {
      "service": "auth-service",
      "currentVersion": "1.7.0-SNAPSHOT",
      "status": "mismatch"
    },
    {
      "service": "user-service",
      "currentVersion": "1.8.0-SNAPSHOT",
      "status": "aligned"
    }
  ]
}
```

The result must distinguish:

- Aligned
- Mismatch
- Unknown
- Unresolved

Do not guess dependency versions when Maven configuration prevents reliable resolution.
