# Task 014 — MCP Server & AI Agent Integration

## Role

Act as a Senior Rust Engineer, MCP Protocol Engineer, Software Architect, and AI Developer Tooling Engineer.

You are implementing **Task 014 — MCP Server & AI Agent Integration** of the Service Orchestrator project.

Your goal is to expose the existing Service Orchestrator application capabilities to AI agents through the Model Context Protocol (MCP).

This must be a production-quality integration, not a demonstration or mock MCP server.

The MCP server must invoke real Application Core use cases.

# 2. Goal

Implement a standards-compliant MCP server that allows AI agents to:

- Discover workspaces and services
- Inspect Git repository state
- Synchronize repositories
- Build services
- Build and install libraries
- Inspect library version alignment
- Start, stop, and restart services
- Inspect and execute configured migrations
- Inspect health status
- Retrieve logs and diagnostics
- Submit long-running operations
- Monitor task progress
- Cancel tasks
- Execute supported environment preparation workflows

The MCP server must use the same Application Core as the Ratatui TUI.

Do not duplicate business logic.

---

# 3. Core Architectural Principle

The intended architecture is:

```text
                    Human Developer
                          |
                          v
                     Ratatui TUI
                          |
                          v
                   Application Core
                          ^
                          |
                      MCP Adapter
                          ^
                          |
                       AI Agent
```

Both interfaces must use the same application capabilities.

The application must remain fully functional without MCP or an LLM.

---

# 4. MCP Specification and SDK

Use the current stable MCP specification supported by the selected Rust SDK.

Prefer the official Rust MCP SDK, `rmcp`, if compatible with the project's requirements.

Before implementation:

1. Inspect the selected SDK version.
2. Verify supported MCP protocol capabilities.
3. Verify stdio transport support.
4. Verify tool registration and schema generation.
5. Verify resource support.
6. Verify prompt support.
7. Verify error handling.
8. Verify lifecycle and cancellation behavior.

Do not invent MCP protocol behavior.

Do not implement a custom JSON-RPC protocol when the SDK already provides the required functionality.

Pin compatible dependency versions and document the selection.

# 5. Single Binary

The existing binary must support:

```bash
service-orchestrator tui
service-orchestrator mcp
```

Both modes must use the same Application Core initialization.

Do not create a separate MCP backend application.

Do not require Node.js or Python to run the MCP server itself.

---

# 6. MCP Transport

Use **stdio** as the primary transport.

The AI client should launch:

```bash
service-orchestrator mcp
```

and communicate through stdin/stdout.

Critical requirement:

**stdout must be reserved exclusively for MCP protocol messages.**

Application logs, startup banners, diagnostics, and debugging output must not be printed to stdout.

Use stderr or configured log files for diagnostics.

Do not require an HTTP server for MVP.

---

# 7. MCP Server Lifecycle

Implement:

1. Load validated configuration.
2. Initialize shared Application Core.
3. Initialize required infrastructure.
4. Initialize MCP adapter.
5. Register tools, resources, and prompts.
6. Start stdio transport.
7. Handle MCP requests.
8. Support graceful shutdown.

Do not start the Ratatui interface in MCP mode.

Do not initialize terminal raw mode in MCP mode.

---

# 8. MCP Architecture

Use a thin adapter structure.

Conceptually:

```text
MCP Transport
      |
      v
MCP Server
      |
      v
Input Validation
      |
      v
Application Use Case
      |
      v
Policy Engine
      |
      v
Task / Workflow Engine
      |
      v
Infrastructure
```

The MCP adapter may perform protocol-level validation and mapping.

Business validation and authorization must remain in the Application Core.

# 9. MCP Tool Design

Tools must have:

- Clear names
- Clear descriptions
- Strict input schemas
- Structured outputs
- Stable error codes
- Appropriate risk classification
- Bounded responses
- No hidden destructive behavior

Prefer domain-specific tools.

Do not expose a generic unrestricted shell execution tool.

# 23. Structured Tool Responses

Use consistent response envelopes where practical.

Example:

```json
{
  "success": true,
  "data": {
    "serviceId": "auth-service",
    "status": "running"
  }
}
```

For long-running operations:

```json
{
  "success": true,
  "data": {
    "taskId": "12345",
    "status": "queued"
  }
}
```

For errors:

```json
{
  "success": false,
  "error": {
    "code": "SERVICE_NOT_FOUND",
    "message": "The requested service does not exist."
  }
}
```

Map these results correctly to the MCP SDK's supported result/error semantics.

Do not confuse application-level operation failures with malformed MCP protocol requests.

# 26. Security and Policy

The MCP server must not bypass Application Core authorization.

Classify operations according to actual risk.

Examples:

- Read-only inspection
- Repository mutation
- Build execution
- Process control
- Database migration
- Destructive Git operations

Do not assume all builds or migrations are harmless.

Maven plugins and npm scripts can execute project code.

Migrations can modify database schemas.

Use the existing policy model.

---

# 27. Confirmation Handling

Some operations may require explicit authorization.

The MCP server must not invent approval or claim that a human confirmed an operation.

If authorization is required, return a structured authorization-required result.

Do not accept an arbitrary `confirmed: true` argument as sufficient proof of approval.

Use the existing trusted authorization mechanism.

If the application does not yet have a secure confirmation mechanism usable by MCP, reject or defer protected operations and document the limitation.

---

# 28. AI Client Trust Boundary

Treat MCP tool inputs as untrusted.

Do not allow an AI client to bypass:

- Path validation
- Git safety checks
- Database target restrictions
- Service operation coordination
- Secret redaction
- Task concurrency limits

The MCP client is not inherently trusted merely because it runs locally.
