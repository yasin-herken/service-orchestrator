## Role

Act as a Senior Rust Engineer, Ratatui Engineer, Terminal UX Designer, and Software Architect.

You are implementing **Task 013 — Ratatui TUI & Interactive Service Management** of the Service Orchestrator project.

Your goal is to build a production-quality terminal user interface that integrates the existing Service Orchestrator capabilities into one cohesive developer experience.

# 2. Goal

Implement a complete, keyboard-first Ratatui interface for Service Orchestrator.

The TUI must allow developers to manage:

- Workspaces
- Services
- Git repositories
- Builds
- Shared libraries
- Database migrations
- Running processes
- Health checks
- Tasks
- Logs

The UI must remain independent from business logic.

The Application Core is the only entry point for application operations.

---

# 3. Core Architectural Rule

The TUI is an adapter.

It must not directly execute:

- Git commands
- Maven commands
- npm commands
- Liquibase commands
- OS processes

Correct architecture:

```text
Ratatui
   |
   v
Application Core
   |
   v
Task / Workflow Engine
   |
   v
Infrastructure
```

Do not duplicate application logic inside UI components.

---

# 4. Application Startup

The binary must support:

```bash
service-orchestrator tui
```

Optionally, running without arguments may launch the TUI.

The startup process should:

1. Initialize terminal safely.
2. Load validated configuration.
3. Initialize Application Core.
4. Initialize required infrastructure components.
5. Initialize Task Engine.
6. Initialize TUI state.
7. Enter the event loop.
8. Restore terminal state on exit.

Do not create a second application initialization path if a reusable bootstrap mechanism already exists.

---

# 5. Terminal Lifecycle

Terminal state must be restored correctly after:

- Normal exit
- Application error
- Ctrl+C
- Panic where recoverable
- Terminal resize
- Interrupted operation

Use appropriate terminal setup and cleanup patterns.

Do not leave the developer's terminal in raw mode after exit.

# 6. TUI Architecture

Use a clean separation between:

- Application state
- UI state
- UI events
- Commands
- Rendering
- Async operation results

Suggested conceptual structure:

```text
TUI
├── App State
├── Event Loop
├── Input Handler
├── Action Dispatcher
├── Screen Router
├── Components
├── Dialogs
└── Renderer
```

Avoid a monolithic UI module.

---

# 7. UI State vs Application State

Keep UI state separate from application state.

UI state includes:

- Selected screen
- Selected row
- Selected services
- Active dialog
- Search query
- Scroll position
- Focused panel
- Active filters

Application state includes:

- Service runtime status
- Git status
- Task status
- Health status
- Process state
- Logs

Do not duplicate application state unnecessarily.

Prefer consuming application queries and events.

# 29. UI Error Handling

Errors must be actionable.

Bad:

```text
Operation failed
```

```text

Operation: Maven clean install

Reason:
Dependency resolution failed.

[View Logs] [Close]
```

Do not hide useful failure details.
